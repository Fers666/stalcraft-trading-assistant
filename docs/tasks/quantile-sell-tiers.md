# ТЗ: калибровка ценовых тиров по квантилям цен сделок (P0-1)

> ⚠ **Поправка 2026-08-16 к названию и к §3.2.** ТЗ называлось «по вероятности исполнения», и поле получило имя `fill_probability` — оба формулируют сильнее, чем то, что измерено.
>
> Замер §2 берёт цены **состоявшихся** сделок и считает их квантиль. Это **ценовая позиция относительно потока сделок**, а не вероятность продажи конкретного лота: величина ничего не знает ни о частоте прихода покупателей, ни о конкурентах, ни о лотах, которые не продались вовсе. Совпали бы они только при условии, что продаётся каждый выставленный лот.
>
> Сами константы `0.94 / 1.00 / 1.06` верны и остаются — неверна была их интерпретация. Формулировка в UI исправлена, имя поля оставлено (переименование не стоит миграции данных). Настоящая вероятность исполнения — `P(продан ≤ H)` по кривой дожития, P1-4 фаза B, см. `docs/tasks/sale-time-prediction-research.md`.

## 1. Задача

Ценовые тиры заданы константами, которые никогда не сверялись с фактом:

```python
fast_price    = int(ref * 0.97)   # «Быстро»
normal_price  = int(ref * 1.00)   # «Обычно»
premium_price = int(ref * 1.05)   # «Премиум»
```

Название «Быстро» обещает быструю продажу, но число под ним не связано ни с какой измеренной вероятностью исполнения. Вся оценка прибыли строится именно на этом тире (`evaluate_lot_profit` → `sell_price = fast["price_per_unit"]`), поэтому ошибка в нём попадает в каждый сигнал.

## 2. Замер и калибровка

**Постановка:** опора — взвешенная медиана сделок варианта за 7 дней до среза. Проверка — цены реальных сделок этого же варианта в следующие сутки. Квантили считаются **внутри варианта**, затем берётся медиана по вариантам.

> **Почему по вариантам, а не по сделкам.** Первая редакция разбора (`profit-algo-review.md` §1.2) усредняла по сделкам и получила `q25 = 0.889`. Это неверная постановка: оборот сосредоточен в нескольких ликвидных вариантах (54 тыс. сделок из 58 тыс. — в одном бакете ликвидности), и пул перевешивается ими. Тир же применяется к варианту независимо от его оборота, поэтому веса должны быть равными по вариантам. Правильное число — **0.937**, а не 0.889.

Шесть срезов за три недели, только сделки прода:

| 2026-08-03 | 516 | 0.944 | 1.000 | 1.057 |
| 2026-08-06 | 562 | 0.939 | 1.000 | 1.068 |
| 2026-08-09 | 550 | 0.933 | 1.000 | 1.056 |

| **Среднее** | | **0.937** | **0.997** | **1.058** |

Разброс между срезами — в пределах ±2 %, тренда нет. Константы брать можно.

## 3. Что меняем

### 3.1 Калиброванные множители

`backend/app/services/analytics/pricing.py`, `make_sell_options()`:

```python
FAST_RATIO    = 0.94   # ~75 % сделок варианта проходят по этой цене или выше
NORMAL_RATIO  = 1.00   # ~50 %
PREMIUM_RATIO = 1.06   # ~25 %
```

`0.97 → 0.94` — единственное содержательное изменение. `1.00` подтверждён замером и остаётся, `1.05 → 1.06` — уточнение в пределах шума, берём ради согласованности с калибровкой.

Дубль тех же множителей в `market_stats.py:644-646` — привести к тем же константам, импортом, а не копией. Сейчас это две независимые копии, и они обязаны совпадать.

### 3.2 Вероятность исполнения в `sell_options`

Добавить в каждый элемент `sell_options` поле:

```python
"fill_probability": 75 | 50 | 25   # процент сделок варианта, проходящих по цене тира или выше
```

Это и есть смысл правки: тир перестаёт быть «скидкой N %» и становится обещанием с измеренной вероятностью. Поле уходит в `artifact_variant_stats.sell_options` и `market_statistics.sell_options` (оба JSONB, миграция не нужна).

### 3.3 Фронт: показать, что означает тир

В блоке «Варианты продажи» карточки предмета (`LotStatCard.tsx:497-519`, `MobileLotStatCard.tsx`) рядом со сроком показать вероятность: «продастся в ~75 % случаев» или эквивалент. Формулировка на усмотрение, но она должна читаться как свойство цены, а не как гарантия.

Только токены из `theme.ts`. Раскладку не менять.

## 4. Что НЕ входит

**Вариантная калибровка квантилей — сознательно отложена.** Замер: корреляция отношения `q25/med` одного варианта между соседними неделями — **0.473**; средняя ошибка предсказания 0.043 против **0.049** у глобальной константы. То есть отдельная колонка, порог выборки и фоллбек купили бы ~12 % точности. Не окупается; при возврате к вопросу — начинать с этих двух чисел.

Остальные пункты плана (`profit-algo-review.md` §3) не трогаются: цензурирование времени (P1-4), EV-ранжирование (P0-3), сторона стакана (P1-5), `signal_outcomes` (P1-7).

## 6. Приложение: запрос для перекалибровки

Повторять раз в месяц либо после заметного сдвига рынка. Подключение — см. `docs/tasks/profit-algo-review.md` §4.

```sql
CREATE TEMP TABLE slices(t timestamptz);
INSERT INTO slices VALUES ('2026-08-03 00:00+03'),('2026-08-09 00:00+03'),('2026-08-14 00:00+03');

SELECT to_char(s.t,'MM-DD') slice, count(*) variants,
       round(percentile_cont(0.5) WITHIN GROUP (ORDER BY g.q25)::numeric,3) fast,
       round(percentile_cont(0.5) WITHIN GROUP (ORDER BY g.q50)::numeric,3) normal,
       round(percentile_cont(0.5) WITHIN GROUP (ORDER BY g.q75)::numeric,3) premium
FROM slices s
CROSS JOIN LATERAL (
  WITH sl AS (
    SELECT item_id, COALESCE(additional_info->>'qlt','0') qlt,
           COALESCE(additional_info->>'ptn','0') ptn, price_per_unit::numeric p, sale_time
    FROM sales_history
    WHERE sale_time >= s.t - interval '7 days' AND sale_time < s.t + interval '1 day'
  ),
  ref AS (SELECT item_id,qlt,ptn, percentile_cont(0.5) WITHIN GROUP (ORDER BY p) med
          FROM sl WHERE sale_time < s.t GROUP BY 1,2,3 HAVING count(*) >= 20)
  SELECT percentile_cont(0.25) WITHIN GROUP (ORDER BY sl.p/ref.med) q25,
         percentile_cont(0.50) WITHIN GROUP (ORDER BY sl.p/ref.med) q50,
         percentile_cont(0.75) WITHIN GROUP (ORDER BY sl.p/ref.med) q75
  FROM sl JOIN ref USING (item_id,qlt,ptn)
  WHERE sl.sale_time >= s.t
  GROUP BY sl.item_id, sl.qlt, sl.ptn HAVING count(*) >= 10
) g
GROUP BY 1 ORDER BY 1;
```

## 7. Оговорки

- Константы откалиброваны на вариантах с **≥ 20 сделками** за окно: у более тонких (5–20, они проходят пол P0-2) разброс цен может быть шире, и `fill_probability = 75 %` для них слегка оптимистична. Измерить это напрямую нельзя — у таких вариантов не набирается 10 сделок в контрольных сутках.
- Горизонт проверки — **одни сутки** после среза. Для тира «Премиум» с ожидаемым сроком продажи в несколько суток это заниженная оценка исполнения: часть таких лотов продалась бы позже окна. То есть 1.06 — консервативная граница, а не потолок.
- Замер не учитывает влияние собственной заявки на рынок: выставляя лот, ты сам сдвигаешь распределение. При объёмах одного игрока эффект пренебрежим, при массовом использовании — нет.
