# ТЗ: Точное определение статуса «продаётся ли предмет на аукционе» по всему каталогу master_items

## Контекст

Сейчас единственный источник статуса торгуемости предмета — поле `master_items.bind_state`
(`status.state` из EXBO GitHub-каталога). Фильтр непродаваемых в
`backend/app/api/v1/endpoints/items.py` считает «не появляется на аукционе» только предметы с
`bind_state IN {PERSONAL_ON_GET, PERSONAL_DROP_ON_GET}` (77 шт. из 2303).

Проблема (подтверждена пользователем): `bind_state` описывает **привязку**, а не **торгуемость**.
Множество предметов, помеченных как продаваемые (квестовые, валюта, чертежи, сюжетные, вендорные —
категории other/misc/supply/device), физически на аукционе не появляются, но проходят текущий
фильтр. Классификация по `bind_state` неверна по существу.

Решение (выбрано пользователем): единоразово пробить каждый `item_id` через Stalcraft API и
определить **реальное** наличие на аукционе через `total` в ответах `/history` и `/lots`, записать
точный статус в БД. Далее использовать этот статус как источник истины в каталоге вместо
эвристики по `bind_state`.

Распределение `bind_state` (для оценки объёма): PERSONAL_ON_USE 1387, NON_DROP 557, NONE 274,
PERSONAL_DROP_ON_GET 51, PERSONAL_ON_GET 26, NULL 8. Всего 2303.

Это **разовый бэкфилл** 2303 предметов, а не непрерывный опрос. Параметры регулярного сбора
(`LOTS_PER_RUN`/`BATCH_SIZE`/`REFRESH_INTERVAL`) не меняются.

## Изменения по слоям

### Backend

#### 1. Схема БД (миграция `0036_master_items_on_auction`)

Добавить в `master_items` 4 nullable-поля:

| Поле | Тип | Смысл |
|---|---|---|
| `on_auction` | `Boolean`, nullable, default NULL | NULL = ещё не проверено, TRUE = торгуется, FALSE = не появляется на аукционе |
| `auction_checked_at` | `timestamptz`, nullable | Момент последней проверки через API (для resumable + periodic re-check) |
| `history_total` | `Integer`, nullable | Последний замер `total` из `/history` (аудит/отладка) |
| `lots_total` | `Integer`, nullable | Последний замер `total` из `/lots` (аудит/отладка) |

Индекс: `CREATE INDEX ix_master_on_auction ON master_items (on_auction);` — фильтр каталога будет
идти по этому полю.

**Обоснование:**
- `on_auction` nullable-boolean, а не boolean-default-false — даёт **resumability**: задача
  обрабатывает `WHERE on_auction IS NULL`, повторный запуск не перепроверяет уже пройденные.
  Различие «не знаю» (NULL) и «точно нет» (FALSE) критично: транзиентная ошибка API не должна
  выглядеть как «не торгуется».
- `auction_checked_at` нужен для необязательного периодического ре-чека (по возрасту записи) и для
  наблюдаемости прогресса.
- `history_total`/`lots_total` — дешёвая отладочная избыточность (по 4 байта): позволяют вручную
  проверить пограничные решения и не гонять API повторно при разборе спорных предметов.
  Если пользователь сочтёт лишним — можно оставить только `on_auction` + `auction_checked_at`
  (см. открытые вопросы).

Модель `MasterItem` в `models.py` — добавить те же 4 колонки и индекс в `__table_args__`.

#### 2. Критерий классификации

Порядок проверки на один предмет (экономия запросов — `/history` первым):

```
1. history = get_auction_history(item_id, region)   # cost 2
   history_total = int(history.get("total", 0))
   если history_total > 0:
       on_auction = TRUE            # был хоть раз продан → торгуется (в т.ч. редкие/сезонные)
       lots_total = NULL (не запрашивали)
       СТОП
2. иначе (history_total == 0):
   lots = get_auction_lots(item_id, region)          # cost 2
   lots_total = int(lots.get("total", 0))
   если lots_total > 0:
       on_auction = TRUE            # новый предмет, ещё без продаж, но выставлен
   иначе:
       on_auction = FALSE           # ни истории, ни лотов → не появляется на аукционе
```

**Почему `/history` важнее и первым:** редкий/сезонный предмет может иметь 0 активных лотов
прямо сейчас, но ненулевую историю продаж → это торгуемый предмет. Текущие лоты вторичны и нужны
только чтобы поймать «новый предмет, выставлен, ещё не продан». Проверка `/history` первой экономит
запросы: у торгуемых предметов (их большинство) хватит одной пары запросов (cost 2), вторая пара
(`/lots`) тратится только на кандидатов в «не торгуется».

**Пограничные случаи:**
- **404 от API** (предмет не существует в системе аукциона / удалён из игры) → `on_auction = FALSE`,
  `history_total = lots_total = 0`, `auction_checked_at = now`. Это валидный отрицательный ответ.
- **Транзиентная ошибка** (5xx, таймаут, сетевой сбой, `TimeoutError` от лимитера, неожиданный 429)
  → **НЕ писать FALSE**. До 2 ретраев с backoff (напр. 2s, 5s). Если не удалось — оставить
  `on_auction = NULL`, залогировать `item_id` + ошибку; предмет попадёт в следующий прогон.
- **401** — обрабатывается внутри клиента (автосброс токена), наружу не всплывает.
- Идемпотентность: запись `on_auction`/`*_total`/`auction_checked_at` через UPDATE по `item_id`,
  повторный проход того же предмета даёт тот же результат.

#### 3. Механизм запуска — Celery-задача + admin-триггер (рекомендация)

Рекомендуемый подход: **Celery-задача `audit_auction_status`, запускаемая admin-эндпоинтом**.

- Задача (в `tasks/collectors.py` рядом с остальными коллекторами, либо новый `tasks/audit.py`):
  - Параметры: `force_recheck: bool = False`, `stale_days: int | None = None`,
    `limit: int | None = None` (для тестового прогона на N предметов).
  - Выборка предметов:
    - обычный прогон: `WHERE on_auction IS NULL` (resumable — только непроверенные);
    - `force_recheck=True`: все предметы;
    - `stale_days=N`: `WHERE on_auction IS NULL OR auction_checked_at < now() - N days`
      (для периодического ре-чека).
  - Обрабатывает предметы **последовательно**, коммит после **каждого** предмета (устойчивость к
    рестарту воркера — прогресс не теряется).
  - Self-throttle: `await asyncio.sleep(AUDIT_REQUEST_DELAY)` между предметами (см. бюджет ниже).
  - Один общий `redis_client` на прогон (как в `collect_all_active_lots`), передаётся в
    `get_auction_lots(..., redis_client=...)`; для `get_auction_history` клиент не
    прокидывается — приемлемо (лимитер создаст своё соединение).
  - Логирование прогресса: каждые ~50 предметов — `INFO` с `checked/total`, счётчиками
    TRUE/FALSE/errors.
  - `bind=True, max_retries=0` (ретраи — внутренние, на уровне одного предмета, чтобы падение на
    одном предмете не рестартовало всю задачу).
- Admin-эндпоинт `POST /api/v1/admin/audit-auction-status` (`get_current_admin`): ставит задачу в
  очередь (`audit_auction_status.delay(...)`), возвращает `{status: "queued", task_id}`.
  Дополнительно `GET /api/v1/admin/audit-auction-status` — прогресс из БД:
  `total`, `checked` (on_auction NOT NULL), `on_auction_true`, `on_auction_false`, `pending` (NULL),
  `last_checked_at`.

**Почему так, а не management-скрипт / синхронный эндпоинт:**
- Переиспользует существующую инфраструктуру (Celery worker, `get_celery_db_session`, `run_async`,
  общий rate limiter) — минимум нового кода.
- Долгий прогон (десятки минут, см. оценку) нельзя держать в HTTP-запросе — Celery выполняет в
  фоне, эндпоинт отвечает мгновенно.
- Resumable «из коробки» через `WHERE on_auction IS NULL` + покоммитный прогресс: рестарт воркера/
  деплой не начинает заново.

**Периодический ре-чек (опционально, НЕ обязательно):** предметы появляются/исчезают с аукциона.
Можно добавить в beat ежемесячный запуск `audit_auction_status(stale_days=30)`. По умолчанию **не
включать** — оставить ручной запуск; решение о периодике за пользователем (см. открытые вопросы).

#### 4. Бюджет API-запросов и оценка времени (ТРЕБУЕТ ПОДТВЕРЖДЕНИЯ ПОЛЬЗОВАТЕЛЯ)

Стоимость в «запросах-единицах» лимитера (не HTTP-вызовах): торгуемый предмет = 2 (только
`/history`), неторгуемый/кандидат = 4 (`/history` + `/lots`).

Границы полного прогона 2303 предметов:
- нижняя (все торгуемые, по одной паре): `2303 × 2 = 4606` ед.;
- верхняя (все требуют обе пары): `2303 × 4 = 9212` ед.;
- реалистичная (~1500 торгуемых + ~800 нет): `1500×2 + 800×4 ≈ 6200` ед.

Резерв лимитера ~345 ед/мин, но выедать его целиком нельзя (конкуренция с непрерывным сбором).
Предлагаемый **бюджет бэкфилла ≈ 100 ед/мин** (25% от 400; вместе с текущими 54.5 → ~154 ед/мин =
~38% лимита, безопасно). Реализуется через `AUDIT_REQUEST_DELAY` между предметами:
при ~2-4 ед/предмет и цели 100 ед/мин → задержка ~1.5–2.4 с/предмет.

Оценка времени полного прогона при бюджете 100 ед/мин:
- реалистично ~6200/100 ≈ **62 минуты**;
- худший случай ~9212/100 ≈ **92 минуты** (~1.5 ч).

Более консервативный бюджет 60 ед/мин → реалистично ~103 мин, худший ~154 мин (~2.5 ч).

Лимитер жёстко гарантирует, что суммарно (сбор + бэкфилл) не превысим 400/мин; self-throttle нужен
лишь чтобы бэкфилл не «съедал» резерв и не тормозил непрерывный коллектор. Значение
`AUDIT_REQUEST_DELAY` вынести константой в задаче. **Параметры непрерывного опроса
(`LOTS_REFRESH_INTERVAL`/`MAX_LOTS_PER_RUN`/`TARGET_CYCLE_SEC`) не трогаем.**

#### 5. Смена фильтра каталога (`items.py`) — двухфазный переход

Trade-off: пока бэкфилл не прошёл полностью, часть предметов имеет `on_auction IS NULL`
(не проверены). Резко переключаться на `WHERE on_auction IS TRUE` нельзя — до завершения бэкфилла
каталог «опустеет».

Рекомендация — **двухфазно**:
- **Фаза A (сразу после миграции, во время/после бэкфилла):** фильтр показывает всё, кроме
  подтверждённо неторгуемого:
  ```
  WHERE on_auction IS NOT FALSE
    AND (on_auction IS TRUE
         OR bind_state IS NULL
         OR bind_state NOT IN {PERSONAL_ON_GET, PERSONAL_DROP_ON_GET})
  ```
  То есть `on_auction = FALSE` скрывает, `TRUE` показывает, `NULL` (ещё не проверен) — падает на
  старую эвристику `bind_state`. Каталог не ломается на переходном периоде.
- **Фаза B (после полного бэкфилла и ручной верификации, когда `pending = 0`):** чистый фильтр
  ```
  WHERE on_auction IS TRUE
  ```
  и удаление `_UNTRADABLE_BIND_STATES`-эвристики из запроса.

`bind_state` как колонка **остаётся** (метаданные из GitHub, синхронизируется каталогом), но
перестаёт быть источником статуса торгуемости. Переключение Фаза A → Фаза B — отдельный маленький
коммит после подтверждения, что бэкфилл завершён (`GET /admin/audit-auction-status` → `pending = 0`).

### Frontend

По умолчанию правок не требуется: `/items` вернёт меньше предметов (уйдёт мусор), контракт
`ItemResponse` не меняется. **Опционально** (по желанию пользователя, отдельной задачей): добавить
`on_auction` в `ItemResponse` и показывать бейдж/фильтр «только торгуемые» в каталоге. В базовый
объём не входит.

- [ ] Полный прогон завершается: `pending = 0` (кроме предметов с устойчивой ошибкой API —

- [ ] (Фаза B, после верификации) фильтр `on_auction IS TRUE`, `bind_state`-эвристика удалена из

## Проблема catalog↔auction id (weapon/armor)

> Раздел-дополнение (2026-07-24). Исследование расхождения «каталожный `item_id` из EXBO ↔
> аукционный `item_id`, под которым реально идут лоты/история». Написан после того, как бэкфилл
> `on_auction` отработал на проде (1445 TRUE / 879 FALSE, errors=0) и выявил ~219 записей
> категорий weapon/armor с нормальными именами (АК-103, ВСС «Винторез», СВД-М, Desert Eagle Mark VII,
> Colt Python, РПГ-7, K2, Scorpion EVO III, Winchester 1887, MG-34, экзоброня…), помеченных
> `on_auction = FALSE`, потому что API по их каталожному `item_id` отдаёт `history=0 / lots=0`.
> При этом «соседние» стволы (АК-105) дают `history=174349`. У проблемных нет TRUE-двойника в каталоге.

### Что установлено (проверяемые факты)

**1. Каталожный `item_id` — канонический id EXBO, не артефакт парсинга.**
`github_parser._parse_item` берёт `item_id` из имени файла (`PurePosixPath(...).stem`). Проверено
прямым чтением JSON-файлов EXBO: внутреннее поле `id` в каждом файле **равно** имени файла:
- АК-103 → `/items/weapon/assault_rifle/7lrz3.json`, внутри `"id": "7lrz3"`;
- АК-105 → `/items/weapon/assault_rifle/zz2rn.json`, внутри `"id": "zz2rn"`;
- Desert Eagle Mark VII → `ly2v2`, Mark XIX → `y32z0` — то же соответствие.
Значит гипотеза «имя файла ≠ настоящий id внутри JSON» **опровергнута**: наш каталог хранит
именно тот id, который EXBO считает идентификатором предмета. Проблема не на уровне импорта.

**2. Это не легаси-дубли в каталоге.** По всему `listing.json` (2328 записей) в категории `weapon`
лишь **1 имя** имеет >1 id, в `armor` — **2 имени**. Проблемные ~219 gear — это предметы с
**уникальными именами и единственным каноническим id**. Классический сценарий «в каталоге лежат
старый (мёртвый) и новый (живой) id одного оружия, живой помечен TRUE» массово **не подтверждается**
(и прямо противоречит наблюдению «у проблемных нет TRUE-двойника»).

**3. `bind_state` для всего gear одинаков и бесполезен как сигнал.** Распределение по категориям
(из `listing.json`):

| Категория | Всего в каталоге | `bind_state` | color/rank |
|---|---|---|---|
| weapon | 352 | 100% `PERSONAL_ON_USE` | veteran 134, master 111, stalker 60, newbie 29, default 14, legend 4 |
| armor | 139 | 100% `PERSONAL_ON_USE` | master 37, veteran 36, default 25, stalker 21, newbie 18, legend 2 |
| attachment | 280 | 100% `PERSONAL_ON_USE` | stalker 74, master 70, veteran 62, newbie 39, default 30, legend 5 |
| backpacks | 21 | 100% `PERSONAL_ON_USE` | stalker 6, veteran 5, master 4, newbie 3, default 2, legend 1 |
| weapon_modules | 3 | 2 `PERSONAL_ON_USE`, 1 `NON_DROP` | default 2, master 1 |

Всё экипируемое gear — `PERSONAL_ON_USE` (привязка при использовании, но продаётся до применения).
`bind_state` не различает «торгуется/нет» внутри gear. Единственный доступный сигнал — `on_auction`,
и `FALSE` **честно** отражает `0/0` от API по данному каноническому id. Вопрос не в механизме
классификации, а в том, тот ли это id.

**4. Наблюдается rank-корреляция (слабая улика, не доказательство).** Рабочий пример АК-105 —
`RANK_STALKER` (низкий тир), нерабочий АК-103 — `RANK_VETERAN` (высокий). В weapon 245 из 352 —
veteran+master (высокий тир). Возможный системный механизм: высокотировые варианты оружия/брони
получаются **апгрейдом** базового предмета, а на аукционе живёт **базовый** `item_id` с рангом в
`additional.qlt`, тогда как отдельный каталожный id высокого ранга на аукционе не торгуется. Это
согласуется и с гипотезой id-mismatch, и с гипотезой «часть gear реально не аукционируется» —
**одно наблюдение не различает эти две причины**.

### Структура лота и почему id нельзя резолвить через API

- Аукционный API (`services/collector/client.py`) имеет **только** три эндпоинта:
  `/{region}/auction/{item_id}/lots`, `/{region}/auction/{item_id}/history`, `/{region}/emission`.
  **Нет** поиска по имени, нет «related/variants», нет «list all traded item_ids». Резолв
  «имя оружия → настоящий аукционный id» через API **невозможен по построению**.
- Лот запрашивается строго ПО `item_id` (id — в URL, а не в теле лота). В коде лот читается только
  по полям `buyoutPrice/startPrice/amount/endTime/additional{qlt,ptn}`
  (`pricing._lot_quality_enchant`, `collectors._collect_lots_for_item`). Даже если в `additional`
  (base64-декод предмета при `additional=true`) присутствует настоящий id — чтобы получить лот, id
  уже надо знать. Классическая проблема «курица-яйцо»: без живого id мы не увидим ни одного лота
  проблемного оружия.
- Единственный источник соответствия «имя ↔ id» — сам каталог EXBO, который и даёт тот id, что
  отдаёт `0/0`. Если гипотеза id-mismatch верна, **надёжного программного пути резолва настоящего
  id нет**.

### Подтверждается ли гипотеза id-mismatch

**Частично, не доказана.** Что за неё: канонический id корректен, но `history=0/lots=0`; есть
прецедент из памяти проекта («передаваемый уровень сезона»: `item_id` искали как «lots минус
master_items» — т.е. на аукционе есть id, которых нет в каталоге). Что против / альтернатива
равной силы: gear целиком `PERSONAL_ON_USE`, и часть высокотировых вариантов может **реально не
аукционироваться** (получается апгрейдом/крафтом, а не покупкой) — тогда `FALSE` **корректен**.
Статические данные (каталог + уже собранные лоты) **не различают** «id-mismatch (B)» и
«честно не торгуется (A)». Для различения нужна наземная правда — см. пробы ниже.

**Важно для решения:** различать A и B для продуктового решения **не обязательно** — рекомендация
по классификации одинакова в обоих случаях (см. ниже), потому что «скрыть gear по `FALSE`» плохо
при B (теряем живой каталог) и приемлемо-ненужно при A (это экипировка, которую игрок всё равно
может искать; просто без рыночных данных). Резолв A/B — отдельное необязательное расследование,
блокирующее только Фазу B, но не текущую митигацию.

### Пробы для подтверждения/опровержения (для deploy/backend-агента, НЕ запускать из researcher)

Порядок — от бесплатного к платному. Массовый прогон не нужен.

**Проба 1 (бесплатно, прод SQL, read-only).** Проверить, есть ли в уже собранных данных
`item_id`, которых нет в каталоге, и сопоставить их имена/лоты:
```sql
-- item_id, встречающиеся в реальных данных, но отсутствующие в каталоге
SELECT DISTINCT cd.item_id
FROM collected_data cd
LEFT JOIN master_items m ON m.item_id = cd.item_id
WHERE m.item_id IS NULL;

SELECT DISTINCT sh.item_id
FROM sales_history sh
LEFT JOIN master_items m ON m.item_id = sh.item_id
WHERE m.item_id IS NULL;
```
Если список пуст — «id из лотов, которого нет в каталоге» в наших данных не наблюдается (косвенно
против B на нашей выборке; но выборка ограничена watchlist). Если непуст — сверить имена этих id
(вручную по EXBO) с «пропавшим» оружием: совпадение = сильное подтверждение B.

**Проба 2 (бесплатно, прод SQL).** Убедиться, что `FALSE` по gear стабилен и не транзиент:
```sql
SELECT category,
       count(*)                                            AS total,
       count(*) FILTER (WHERE on_auction IS TRUE)          AS true_cnt,
       count(*) FILTER (WHERE on_auction IS FALSE)         AS false_cnt,
       count(*) FILTER (WHERE on_auction IS NULL)          AS null_cnt
FROM master_items
WHERE category LIKE 'weapon%' OR category LIKE 'armor%'
   OR category LIKE 'attachment%' OR category LIKE 'backpacks%'
   OR category LIKE 'weapon_modules%'
GROUP BY category ORDER BY category;
```
Плюс срез FALSE-gear по rank/color (`master_items.color`) — проверить rank-корреляцию из п.4 на
полных данных: если FALSE резко смещён к veteran/master, это усиливает механизм «база торгуется,
высокий тир — нет».

**Проба 3 (наземная правда, дёшево, вручную/community).** Открыть в живой игре аукцион по 2–3
проблемным предметам (АК-103, Winchester 1887). Если лоты есть — предмет торгуется под **другим**
id → гипотеза B подтверждена, а `additional`-payload реального лота (или база данных предмета в
игре) даст настоящий id. Если лотов нет — `FALSE` корректен (гипотеза A). Это **самый дешёвый
и решающий** источник истины; рекомендуется до любых доп. API-проб.

**Проба 4 (платно, ограниченно, ~80–160 ед лимитера, разово).** Прогнать ре-чек по выборке 20–40
FALSE-gear с известными именами (`audit_auction_status(limit=…, force_recheck=True)` по отобранному
списку) — подтвердить, что `0/0` стабильно. По сути уже подтверждено бэкфиллом (errors=0);
дополнительная ценность низкая, делать только если Проба 3 недоступна.

### Рекомендация по классификации gear (архитектурное решение)

**Не доверять `on_auction = FALSE` для всего класса экипируемого gear и держать эти предметы
видимыми в каталоге.** Обоснование — робастность к неопределённости A/B (см. выше) и к rate-limit
(резолв через API невозможен).

Класс gear определяется уже существующей константой в `github_parser._SINGLE_CATEGORIES` =
`{"weapon", "armor", "attachment", "weapon_modules", "backpacks"}` — это ровно набор экипируемой
снаряги и ровно категории под риском. Рекомендуется завести **единый источник** этого набора
(вынести в общий модуль/константу) и использовать его и в парсере, и в фильтре каталога, чтобы
список не разъезжался.

Два варианта реализации (рекомендуется **Вариант 1**):

- **Вариант 1 (рекомендуемый) — расширить gear-exempt в фильтре `items.py`.** Текущая временная
  митигация исключает из скрытия только `weapon%`/`armor%`. Расширить `_gear_exempt` на все 5
  gear-категорий. Плюсы: точечно, не трогает данные бэкфилла, `history_total`/`lots_total`
  остаются для аудита, легко откатить когда id-проблема решится. Минус: `FALSE` по gear остаётся
  в БД как «низкодостоверный», нужно помнить, что для gear он не означает «скрыть».
- **Вариант 2 — не писать FALSE для gear на этапе аудита** (в `_classify_item`/`audit_auction_status`
  оставлять gear в `NULL` при `0/0`, а не `FALSE`). Плюс: `FALSE` в БД везде означает одно и то же
  («точно не торгуется»), фильтр не нуждается в gear-исключении. Минусы: теряем факт «API вернул
  0/0» (можно сохранить в `history_total/lots_total`, но `on_auction=NULL` смешает «gear 0/0» с
  «ещё не проверено»); меняет семантику задачи аудита. Менее предпочтителен.

В обоих вариантах `history_total`/`lots_total` остаются заполненными — по ним всегда видно, что
API реально ответил 0/0, для будущего разбора.

### Расширение scope: attachment / backpacks / weapon_modules (ДА, расширять)

Текущая временная митигация в `items.py` (`_gear_exempt`) покрывает **только** `weapon%`/`armor%`.
Но `attachment` (280 предметов, из них по данным задачи ~128 FALSE), `backpacks` (21, ~10 FALSE) и
`weapon_modules` (3) — тот же класс `PERSONAL_ON_USE`-экипировки и подвержены **идентичному** риску
ложного `FALSE`. Сейчас их FALSE-записи **скрываются** из каталога и могут быть ложно-отрицательными
(модификаторы, рюкзаки, модули оружия реально торгуются на аукционе). **Рекомендация: расширить
`_gear_exempt` на все 5 категорий** (weapon, armor, attachment, weapon_modules, backpacks) —
единым набором `_SINGLE_CATEGORIES`. Это отдельное, дешёвое и безопасное изменение фильтра;
рекомендуется применить сразу (не ждать резолва id-проблемы).

### Влияние на Фазу B (условие безопасного перехода на `on_auction IS TRUE`)

Чистый фильтр `WHERE on_auction IS TRUE` (Фаза B из основного ТЗ) **нельзя** включать, пока gear
трактуется по `on_auction`: это скроет ~219+ реально нужных предметов экипировки. Условия для
безопасной Фазы B:

1. **Либо** гипотеза A подтверждена (Проба 3/community: проблемное gear действительно не
   аукционируется) — тогда `FALSE` по gear корректен и его можно скрывать; Фаза B применима как есть.
2. **Либо** для gear вводится отдельное правило и Фаза B формулируется как
   `on_auction IS TRUE OR (category ∈ _SINGLE_CATEGORIES)` — т.е. строгий фильтр по `on_auction`
   применяется только к **не-gear**, а gear всегда видим (текущая митигация без ветки `bind_state`).
   Это наиболее вероятный практичный исход при неразрешённой неопределённости.
3. **И в любом случае** — `pending = 0` по не-gear категориям (бэкфилл довершён), плюс выборочная
   ручная верификация каталога.

Рекомендуемый практический путь: сейчас — Вариант 1 (расширенный gear-exempt, все 5 категорий);
Фаза B — по формуле из п.2 (gear вне строгого фильтра), пока/если Проба 3 не докажет гипотезу A.
