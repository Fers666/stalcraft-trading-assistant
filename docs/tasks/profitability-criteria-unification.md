# ТЗ: Единый принцип выгодности на всём портале

## Контекст

Вопрос пользователя: «не должны ли все критерии выгодности на портале считаться по одному
принципу — и принцип ленты сейчас самый правильный».

Слой **формул** уже единый: `evaluate_lot_profit` / `make_sell_options` / `compute_reference` /
`classify_risk` живут в `backend/app/services/analytics/pricing.py`, и лента, Избранное и Радар
зовут одни и те же функции. Расходится слой **решения** — какими аргументами их зовут и по чему
потом ранжируют. Три оси расхождения ниже сводятся на принцип ленты, четвёртая (вероятность
продажи) сводиться **не должна до замера** — обоснование в §Ось 4.

### Где именно расходится (проверено по коду)

| Ось | Лента | Избранное (`profitable_lots.py`) | Радар (`market_radar.py`) |
|---|---|---|---|
| Допуск по тирам | все три, `tiers=TIER_ORDER` (`feed_collector.py:542`) | только `fast` (умолчание, `:290`) | только `fast` (умолчание, `:158`) |
| Ранжирование | `ev_profit` (ожидаемые рубли) | `profit_per_hour` (`:308`) | `profitable_offers_count` (`:407`) |
| Опора | вариант `qlt×ptn` всегда (`artifact_variant_stats`) | вариант **только** если пользователь задал фильтр (`:196-245`), иначе предмет целиком | предмет или бакет фильтра, по медиане продаж |
| Вероятность продажи | `FEATURE_POS` (позиция в стакане, `feed_collector.py:595-603`) | `FEATURE_RATIO` (`pricing.apply_survival`) | вероятности нет вовсе (`make_sell_options` без `survival`, `:382`) |

Принцип ленты в одной строке: **допускай лот по любому тиру, помечай каким; ранжируй по
ожидаемым рублям, а не по «сколько дадут, если продастся»; считай опору по варианту, а не по
предмету.**

## Что НЕ входит в объём (и почему)

- **Полная пагинация `/lots` для watchlist.** `raw_lots` снапшота обрезан до **200 самых
  дешёвых** лотов (`tasks/collectors.py:413`, `sorted(lots, key=lot_price_per_unit)[:200]`).
  Полную пагинацию делает только свип ленты по своему набору 382 предметов — поэтому позиция
  лота в стакане (`queue_rank`) для предметов вне набора физически недоступна. Достроить её
  значило бы увеличить расход API, а бюджет выбран (~340 из 400 ед/мин) → **стоп-фактор,
  отдельное решение пользователя** (`CLAUDE.md`, правило про `LOTS_PER_RUN` / `BATCH_SIZE` /
  `REFRESH_INTERVAL` / `FEED_BUDGET_UNITS_PER_MIN`). Для watchlist обрезка не мешает: 200 самых
  дешёвых — ровно те лоты, которые интересны покупателю.
- **Унификация вероятности продажи (Ось 4)** — только после замера, см. отдельный раздел.
- **Изменение самих формул** (`pricing.py`): они уже общие, трогать нечего.

## Влияние на расход Stalcraft API

**Нулевое во всех этапах.** Ни одна ось не добавляет запросов к аукциону: все расчёты идут по уже
собранным снапшотам (`collected_data.raw_lots`), `sales_history` и `lot_observations`. Не меняются
`LOTS_PER_RUN`, `BATCH_SIZE`, `REFRESH_INTERVAL`, `FEED_BUDGET_UNITS_PER_MIN`, состав и частота
Celery-задач. Подтверждение пользователя по rate limit **не требуется** — требуется по продуктовым
эффектам (объём уведомлений, порядок Радара), они отмечены в тексте.

Цена этапов — CPU в цикле коллектора (перебор трёх тиров вместо одного, группировка продаж по
вариантам) и объём Redis-payload сигналов. Оба на порядки ниже текущих значений.

# Этап 1 — Избранное: допуск по трём тирам + ранжирование по `ev_profit` (Оси 1 и 2)

Оси 1 и 2 поставляются **вместе, одной правкой**. Раздельно они вредны: три тира без ev означают
«стало больше сигналов, и непонятно, какие из них стоят внимания» — пользователь получит рост
числа лотов без инструмента приоритизации. Именно эту пару лента и внедрила в `e497dda`.

## Backend

### 1.1 Допуск по трём тирам (`services/profitable_lots.py`)

`evaluate_lot_profit(...)` в цикле по лотам (`:290`) получает `tiers=TIER_ORDER` (импорт из
`pricing`). Возвращаемый `tier_used` уже кладётся в лот через `**evaluated` — новых полей не надо.

Что при этом **не** меняется и должно быть проверено:

- Персональный порог `min_profit_margin_percent` продолжает применяться — он проверяется
  **внутри каждого тира** (`_evaluate_at_tier`: `profit_pct < min_margin_pct × RISK_MARGIN_MULT`).
  Порог не ослабляется, меняется только множество цен, против которых он проверяется.
- `margin_adj_pct` — поле ленты (`feed_collector.py`), в сигналах его нет; ничего не трогаем.
- `breakeven_per_unit`, `ref_used` — считаются как раньше (`ref_used` всегда цена `normal`).

**Осознанный побочный эффект.** Лот, выгодный только по цене между старым тиром `0.97` и новым
`0.94`, до этого отвергался (`backend/tests/test_sell_tiers.py:137`); теперь он вернётся в
Избранное — но помеченный тиром `normal`/`premium` и с `ev_profit`, который учитывает, что такая
цена исполняется в 74.5 % / 49.0 % случаев против 81.3 % у `fast` (замер ТЗ
`feed-multi-tier-admission.md` §2.2). Это не откат калибровки, а перевод её из «отбросить» в
«показать с честной ценой и вероятностью».

### 1.2 Ранжирование по `ev_profit`

Добавить в каждый лот сигнала поле `ev_profit` (ожидаемая прибыль **всего лота** в рублях) и
сортировать по нему:

```python
profitable.sort(key=lambda l: (
    l["ev_profit"] is None,          # без измеренной вероятности — в конец
    -(l["ev_profit"] or 0),
    -(l["profit_per_hour"] or 0),    # прежний ключ как вторичный
))
```

Ответ на «что делать, когда вероятность не измерена»: **`ev_profit = None` и в конец списка**,
внутри хвоста — прежний порядок по `profit_per_hour`. Подставлять `p = 1` нельзя — это вернуло бы
допущение «продастся обязательно», ради снятия которого и заводилась кривая дожития
(`api/feed.ts:41-48`, `models.py` LotObservation). Того же правила держится лента
(`ev_profit … nulls_last`, `feed.py:422`).

Формула — та же, что у ленты, и **вторая копия не заводится**. Вынести в `pricing.py` одну
функцию, которую зовут оба места:

```python
def expected_value(scenarios: dict[str, tuple[int, float | None]]) -> int | None:
    """max по сценариям int(p/100 * value); сценарий без измеренной p не участвует."""
```

`feed_collector.py:630-640` переписывается на вызов этой функции (поведение обязано остаться
побитово тем же — см. приёмку), `profitable_lots` строит свои сценарии так же:

- цена тира `tier_used` — `evaluated["sell_price_used"]` (в ней уже поправка на пачку);
- цены остальных тиров — `tier_prices(ref)[tier]`;
- `value = int(price × amount × (1 − COMMISSION)) − buyout_price`;
- `p` — `p_sold_6h` соответствующей опции из `sell_options` (они уже приходят с вероятностью:
  `make_sell_options(..., survival, item_class)` вызывается с `survival`, `profitable_lots.py:245`).

Вероятность здесь берётся из `FEATURE_RATIO` — то есть та, что есть сегодня. Ось 4 её может
заменить позже, и `ev_profit` улучшится сам, без переписывания этого кода. Ранжирование при этом
устойчиво к возможной ошибке калибровки: по замеру в `models.py` (docstring `SurvivalCalibration`)
кривая промахивается в **уровне** процентов, но **порядок страт сохраняет** — а ранжированию нужен
только порядок.

### 1.3 Контракт `/monitoring/signals`

`SignalLot` (`api/v1/endpoints/monitoring.py:597-609`) уже содержит `tier_used`,
`sell_price_used`, `breakeven_per_unit`, `ref_used` — **схема для Оси 2 не меняется**, меняются
только значения. Для Оси 1 добавить два необязательных поля: `ev_profit: int | None`,
`p_sold_6h: float | None` (вероятность тира, которым лот прошёл, — без неё `ev_profit` в UI
нечем объяснить). Изменение аддитивное, старые клиенты не ломаются.

Маскирование по тарифу (`masked(...)`) на новые поля **не распространять**: они уровня лота, а
маскируется 7-дневная статистика уровня предмета. `lots` уже не маскируется.

### 1.4 Уведомления (Telegram + web push)

Читатели сигналов — `telegram_bot/bot.py:243` (`handle_profitable_lot`) и
`push_service/consumer.py:101` (`render_profitable_lot`). Оба берут payload события, а не Redis-
опрос, и итерируют `signal["lots"]` целиком с дедупом по лоту — **изменение порядка сортировки их
не ломает**, проверено по коду.

Что ломается по смыслу и требует правки:

1. **Объём уведомлений.** У пользователя с `min_profit_margin_percent = 0` (умолчание) допуск по
   трём тирам означает порог «купить дешевле `ref × 1.06 × 0.95 = ref × 1.007`» вместо
   «дешевле `ref × 0.893`». Число уведомляемых лотов вырастет кратно.
   **Решение: событие `profitable_lot` публикуется только для лотов с `tier_used ∈ {fast, normal}`**
   (одно условие в `tasks/collectors.py:548`, где формируется payload; сам сигнал в Redis и в
   карточке остаётся полным, со всеми тремя тирами). Обоснование — та же асимметрия, что уже
   принята в ленте: `premium` не даёт основания будить телефон, потому что это цена с 49 %
   вероятностью продажи за 6 часов и сроком ожидания (`CLAUDE.md`: горячим предмет делают только
   `fast + normal`). Пользователь ничего не теряет: лот виден в карточке.
2. **Текст сообщения не говорит, каким тиром лот прошёл.** `build_lot_message`
   (`telegram_bot/bot.py:96-139`) печатает все три тира с ✅/❌ — для лота, прошедшего по
   `normal`, строка `fast` будет ❌, и сообщение выглядит противоречиво. Добавить параметр
   `tier_used` и пометку у соответствующей строки (например ` ◀ по этому тиру лот прошёл`).
   Формат остальных строк не менять.
3. **Web push печатает прибыль чужого тира — существующий дефект.** `render_profitable_lot`
   считает выгоду от `_best_sell_net(sell_options)` = максимальный `net_price_per_unit`, то есть
   **всегда от `premium`**, независимо от того, каким тиром лот прошёл
   (`push_service/consumer.py:92-108`). Сегодня это завышает обещание на всех лотах; с Осью 2 —
   ещё и рассинхронит push с карточкой. Заменить на `lot["sell_price_used"] × (1 − COMMISSION)`,
   то есть на ту же цену, из которой посчитан `lot["profit"]`.

2. Тот же лот до правки в сигналах отсутствовал (проверить на бэкапе payload'а или пересчётом со

3. `ev_profit` лота сигнала = `int(p_sold_6h/100 × profit_total)` того сценария, который дал

   `sell_options` того же сигнала.
4. Лоты с `ev_profit = None` стоят **после** всех лотов с числом; внутри хвоста порядок —

5. Байтовая неизменность ленты после выноса `expected_value` в `pricing.py`: до/после правки

   прогона `collect_artifact_lots` на одинаковых входных данных либо юнит-тестом на фикстуре).
6. Telegram: сообщение по лоту тира `normal` содержит пометку у строки `normal`; лот тира
   `premium` уведомления **не порождает** (ни Telegram, ни push), но виден в карточке.
7. Web push по лоту тира `fast`: сумма в теле = `sell_price_used × 0.95 − buyout_per_unit`,
   а не разница от `premium`-цены.
8. Карточка Избранного (десктоп + мобайл) на лоте тира `normal`: метка тира в строке,
   мобильная подпись «прибыль / шт (нормально)», числа сходятся с колонкой того же тира.

# Этап 2 — Избранное: вариантная опора всегда (Ось 3)

## Проблема

`compute_signals_for_entry` считает опору по варианту **только** если пользователь сам задал
`quality_filter`/`enchant_filter` (`profitable_lots.py:196-245`). Без фильтров опора берётся по
предмету целиком, а «предмет целиком» смешивает разные товары: довод записан в самом коде —
у Магмы глобальный минимум **145 тыс. против 9.5 млн** для качества «Особый». Следствие: лот
дешёвого качества выглядит сверхвыгодным против общей опоры, лот дорогого — убыточным.

## Ключевой вопрос — как показывать карточку, у которой вариантов много, а карточка одна

Постулировать ответ нельзя, поэтому вот разбор.

**Отвергнуто — «считать по варианту самого дешёвого/частого лота»:** одна опора на разнородные
лоты остаётся той же ошибкой, только менее заметной.

**Отвергнуто — «карточка догружает `/monitoring/item?quality_filter=…` при выборе строки»:**
лишний round-trip на каждый клик и вторая точка правды о ценах варианта.

**Принято — «сигнал считается по варианту каждого лота, карточка агрегирует по выбранной
строке».** Это ровно та схема, что уже работает в ленте (там опции приходят из `/feed/variant`
для конкретного `qlt×ptn`), и она ложится на существующее поведение карточки: клик по строке
«Выгодных лотов» уже пересчитывает блок «Варианты продажи» от выбранного лота
(`LotStatCard.tsx:133`, подпись «↳ Кликни строку»). Значит вариант выбранной строки естественно
определяет и цены блока — новых взаимодействий не появляется.

## Форма данных

Сигнал получает карту вариантов + ссылку у лота:

```
signal.variants = { "4:0": {ref, ref_source, ref_confidence, ref_samples, trend, trend_pct,
                            risk, volatility_7d, volume_7d, sell_options, ref_scope}, ... }
signal.lots[i].variant_key = "4:0"     # f"{qlt}:{ptn}"
```

Верхнеуровневые `ref` / `sell_options` / `risk` **остаются** (предметный уровень) — их читают
графики и «Динамика цен», где предметный смысл верен. Потребители, которым нужен вариант, читают
`variants[lot.variant_key]`.

- **Источник данных — не `artifact_variant_stats`.** Эта таблица покрывает только набор ленты
  (`feed_scope_clause()`, 382 предмета), а в Избранное можно добавить что угодно. Считаем из тех
  же строк `sales_30d`, которые функция уже загружает одним запросом
  (`profitable_lots.py:159-170`): группируем по `(qlt, ptn)` из `additional_info` тем же
  предикатом, что и `_build_sales_filter`, и для каждого варианта, у которого в снапшоте есть
  лоты, гоняем существующую цепочку `weighted_reference → compute_reference → make_sell_options`.
  **Дополнительных SQL-запросов и запросов к API — ноль.**
- **Явный фоллбек (обязателен).** Покрытие `qlt`/`ptn` в `additional_info` неполное, поэтому
  вариантная опора часто окажется `below_floor`. Тогда лот считается по **предметной** опоре, как
  сегодня, и вариант помечается `ref_scope: "item"` (иначе `"variant"`). Без фоллбека Избранное
  молча потеряло бы сигналы там, где они сейчас есть, — недопустимая регрессия: пользователь сам
  добавил предмет и ждёт ответа, а не тишины.
- Ветка с фильтрами (`entry.quality_filter is not None`) становится частным случаем общей: один
  вариант в карте. Логику не дублировать — переиспользовать.

## Критерии приёмки Этапа 2

1. Watchlist-запись **без фильтров** на предмете с разбросом цен по качеству (Магма или
   аналогичный): у лотов разных `qlt` в сигнале разные `variant_key`, и `variants[k].ref` каждого
   равен опоре, посчитанной по продажам **того же** `qlt` (сверить SQL по `sales_history` за 7д
   с тем же предикатом `_build_sales_filter`).
2. Лот дешёвого качества больше не считается выгодным против опоры дорогого: конкретный лот,
   который до правки давал `profit_pct` в разы выше реального, после правки либо исчезает, либо
   получает прибыль по своей опоре. Зафиксировать пару «было/стало» в отчёте QA.
3. Вариант без достаточной статистики: `ref_scope = "item"`, сигнал по его лотам **сохранился**
   (не пропал), в карточке видна пометка об опоре по предмету.
4. Запись **с** фильтрами: числа до и после правки совпадают до рубля (её ветка была вариантной
   и раньше) — это главный регрессионный якорь.
5. Telegram по лоту качества X показывает цены варианта X, а не предмета.
6. Паритет с лентой на предмете из набора ленты: для одного и того же `lot_key`, `amount = 1`,
   `tier_used` и `profit` сигнала и строки ленты совпадают. После Этапа 2 расхождение опор
   между лентой и Избранным должно исчезнуть — соответственно, абзац «Известное легитимное
   расхождение» в `docs/BUSINESS_LOGIC.md` §18 сокращается до случая `amount > 1`
   (`batch_stats` варианта против `batch_stats` предмета — это расхождение остаётся).

# Этап 3 — Радар (Оси 1 и 2, только вместе) — требует подтверждения пользователя

## Почему Ось 2 в Радаре нельзя включать в одиночку

`_count_profitable_offers` зовёт `evaluate_lot_profit` с `min_margin_pct=0.0`
(`market_radar.py:158-161`). Сегодня, при одном тире `fast`, лот считается выгодным при
`buyout < ref × 0.94 × 0.95 = ref × 0.893`. С тремя тирами условие станет
`buyout < ref × 1.06 × 0.95 = ref × 1.007` — то есть «дешевле опоры». Счётчик распухнет почти на
всех бакетах, а поскольку **по нему идёт сортировка страницы** (`:407`) и флаг подсказок
онбординга `has_profitable` (`:281`), Радар выродится в «у кого больше лотов на рынке».

## Рекомендация

Включать три тира **одновременно** со сменой ключа сортировки на деньги:
`ev_offers_total` = сумма `ev_profit` по выгодным лотам бакета (та же функция
`pricing.expected_value` из Этапа 1). `profitable_offers_count` остаётся **отображаемым**
числом — метрика «сколько сейчас можно купить» пользователю понятна и полезна, просто перестаёт
быть ключом порядка.

Цена: `_calculate_market_radar_aggregate` должен получить кривую дожития
(`load_survival(db)` один раз на пересчёт агрегата) и передавать её в `make_sell_options`
(`:382`) — сейчас Радар зовёт её **без** `survival`, поэтому вероятностей у него нет вовсе и
`ev` без этого не посчитать. Агрегат кэшируется 60 с (`CACHE_TTL`), так что чтение таблицы
дожития раз в минуту — незаметно.

**Требует подтверждения пользователя:** меняется видимый порядок страницы «Радар рынка» и
семантика подсказок онбординга. Это продуктовое решение, а не выравнивание формул.

## Приёмка Этапа 3

1. `profitable_offers_count` бакета вырос (три тира) — зафиксировать «было/стало» на 3 бакетах.
2. Порядок страницы соответствует `ev_offers_total` убыв., `null` — в конец.
3. Подсказки онбординга (`get_watchlist_suggestions`, cache-read-only) не начали греть кэш и
   работают на том же агрегате.
4. Время пересчёта агрегата не выросло более чем на десятки миллисекунд (лог/замер).

# Ось 4 — вероятность продажи: НЕ унифицировать, сначала замер

## Почему не сейчас

Лента считает вероятность по **позиции цены в живом стакане** (`FEATURE_POS`), всё остальное —
по **отношению цены к опоре** (`FEATURE_RATIO`, `pricing.apply_survival`). На «Солнце» они
разошлись на 24 п.п. (`POS` 32.04 % против `RATIO` 56 %). В коде выбор описан как «по силе
признаки сопоставимы», то есть паритет когда-то измерялся, — значит вопрос не «какой признак
правильнее по смыслу», а «какой лучше калиброван на свежих данных». Свести их волевым решением
означало бы заменить одну неизвестную точность на другую и потерять возможность сравнить.

Дополнительный ограничитель: `FEATURE_POS` требует полного стакана варианта, который есть только
у набора ленты (см. §«Что НЕ входит в объём»). Даже если замер выберет `POS`, для предметов вне
набора всё равно нужен `RATIO`-фоллбек — то есть унификация будет «POS там, где есть стакан».

## Методика замера (данные уже копятся, нового кода не нужно)

Обе оценки **уже сверяются** с фактом: `survival.evaluate_calibration` (`survival.py:422-520`)
проходит по `_FEATURE_SQL`, где есть и `pos`, и `ratio`, и пишет в таблицу
`survival_calibration` строки `(class, feature, bucket, horizon_h, window_from, window_to, n,
predicted, realized, error_pp)`. Обучающее и проверочное окна не пересекаются по построению.
`lot_observations` несёт оба признака на одной строке (`ref_price_at_seen` → ratio,
`queue_rank` + `variant_live_lots` → pos) и факт (`outcome`), поэтому сравнение честное — один и
тот же набор лотов.

Замер = **read-only SQL** по накопленным окнам:

```sql
SELECT feature, class,
       SUM(n)                                   AS n,
       ROUND(SUM(ABS(error_pp) * n) / SUM(n), 2) AS mae_pp,   -- точность
       ROUND(SUM(error_pp * n) / SUM(n), 2)      AS bias_pp,   -- знак ошибки
       COUNT(DISTINCT window_from)               AS windows
FROM survival_calibration
WHERE horizon_h = 6
GROUP BY feature, class;
```

Плюс проверка **различающей силы** (признак может быть точным и при этом бесполезным, если все
страты дают одно число):

```sql
SELECT feature, class, MAX(realized) - MIN(realized) AS spread_pp
FROM survival_calibration WHERE horizon_h = 6 GROUP BY feature, class;
```

**Критерий победы** (объявить до замера, чтобы не подгонять):

1. не меньше **3 непересекающихся проверочных окон** и `SUM(n) ≥ 300` на признак в классе
   `artefact` (иначе замер сам по себе шум; `MIN_CALIBRATION_N` фильтрует страты, но не итог);
2. победитель — меньший **взвешенный MAE** при разнице **≥ 3 п.п.**; разница меньше = ничья;
3. при ничьей выигрывает признак с менее отрицательным `bias_pp` (отрицательный = обещали
   больше, чем вышло, то есть ошибка в опасную для пользователя сторону);
4. при ничьей и по bias — выигрывает больший `spread_pp` (лучше различает страты);
5. если победил `POS` — сводим карточку на `POS` там, где стакан доступен, `RATIO` остаётся
   фоллбеком; если победил `RATIO` — на него переводится лента (это дешевле: убрать вызов
   `_scenario`, а не строить стакан).

Замер оформляется **отдельной задачей** и делается не раньше, чем накопятся окна. До его
результата ни одна строка про вероятности не меняется.

  позиции плановой цены в стакане (`FEATURE_POS`), карточка/Избранное/Радар — по отношению цены
