# ТЗ: Параллельные запросы в прогоне watchlist + счётчик ошибок лимита за сутки

**Статус:** ТЗ готово, реализация не начата
**Дата:** 2026-08-21
**Повод:** пользовательский запрос — (A) «прогон watchlist ходит в API по очереди,
упирается в ожидание сети, а не в лимит — распараллелить»; (B) «хочу видеть в
админ-панели, сколько было ошибок лимита за последние сутки».

Две части в одном ТЗ сознательно: **Часть B — измерительный прибор для Части A.**
Без суточной истории расхода и счётчика 429 нельзя доказать, что ускорение
сборщика не вывело нас за лимит внешнего API. Порядок выкатки — B, потом A
(см. §7).

## 3. Часть A — параллельные запросы внутри прогона

### 3.1. Что происходит сейчас

`backend/app/tasks/collectors.py`:

- `collect_all_active_lots` (L45–166) — читает весь активный watchlist, схлопывает
  в `due_pairs` по `(item_id, region)` (L84–97), считает динамический батч
  (L100–105), затем **последовательный** цикл L110–122: `await _collect_lots_for_item(...)`
  и `await asyncio.sleep(LOTS_REQUEST_DELAY)` между итерациями.
- `_collect_lots_for_item` (L338–441) делает всё подряд: `rate_limiter.acquire()`
  внутри клиента → HTTP `/lots` (~1.1 с) → `api_cache.set_lots` → расчёт снапшота →
  `db.add` → `entry.last_successful_check = now` → `await db.commit()` →
  `_publish_signals` (L442+, 4–5 запросов в БД + Redis + RabbitMQ).
- L125–131 — второй проход: `last_successful_check` проставляется **всем** записям
  собранных пар (у одной пары могут быть записи разных пользователей).

Арифметика прогона сходится: 46 пар × (1.1 с HTTP + 0.2 с пауза) ≈ 60 с ≈
измеренные 61.5 с. **Доля времени, занятая работой с БД, — единицы процентов**;
всё остальное — последовательное ожидание сети. Свободно ~60 % лимита API.

Следствие: расписание `timedelta(seconds=20)` с `expires: 20` (`celery_app.py:40-44`)
бессмысленно — прогон втрое длиннее такта, 7 тиков из 15 выбрасываются, частоту
фактически задаёт длительность прогона.

### 3.2. Ключевой факт: расход задаётся кругом, а не скоростью прогона

Каждая пара стоит 2 единицы (`TokenCost.LOTS`) за обход. При `P` уникальных парах
и круге обновления `C` секунд:

```
units_per_min = 2 · P · 60 / C
```

При `P = 137`: `C = 165 с → 100 ед/мин` (совпадает с замером), `C = 110 → 150`,
`C = 60 → 274`. **Ускорение прогона само по себе не экономит и не тратит ни одной
единицы** — оно снимает ограничение «прогон не влезает в такт» и делает круг
управляемым параметром. Поэтому степень параллелизма и целевой расход — два
независимых решения, и второе вынесено в §1 на подтверждение.

Второе следствие: при росте watchlist текущая формула батча
(`ceil(due / runs_per_cycle)`, L100–105) увеличивает расход **линейно и без
потолка**. Отсюда требование ввести `WATCHLIST_BUDGET_UNITS_PER_MIN` как жёсткий
кап батча — при росте числа пар должен деградировать круг, а не соблюдение лимита.

### 3.3. Архитектурное решение: разделить фазу сети и фазу записи

**Проблема, которую нужно обойти:** `AsyncSession` SQLAlchemy **не рассчитан на
конкурентные корутины** — одна сессия обслуживает одно соединение и один
транзакционный контекст; параллельные `execute`/`commit` в одной сессии дают
`InterfaceError` / `IllegalStateChangeError` либо тихо перемешанные транзакции.
Прецедент в этом же файле: `collect_all_history` (L200–226) параллелится **шестью
воркерами, у каждого своя сессия**, и в комментарии это прямо оговорено.

Рассмотрены три варианта.

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **B1. Чанки со своей сессией** (как `collect_all_history`) | `N` воркеров, у каждого `get_celery_db_session()` и свой кусок пар | шаблон уже есть в коде | `get_celery_db_session` создаёт **отдельный engine с NullPool на каждый вызов** (`db/session.py:38-64`) — 4 новых движка и 4 соединения к Postgres **три раза в минуту** (у истории это раз в час); `entry`-объекты придётся перечитывать в каждой сессии; медленный предмет тормозит весь свой чанк |
| **B2. Разделить фазы: параллельный fetch → последовательная запись** ✅ | фаза 1 — только HTTP + запись в Redis-кэш, `asyncio.gather` + `Semaphore(N)`; фаза 2 — прежний последовательный код на **одной** существующей сессии | вопрос безопасности сессии снят полностью, а не обойдён; одно соединение к Postgres; канал RabbitMQ и `_publish_signals` тоже остаются последовательными (aio-pika-канал так же не рассчитан на конкурентные публикации); параллелится ровно то, что тормозит (~98 % времени) | данные первого предмета к моменту записи «стареют» на длительность фазы 1 (~8–10 с) — лечится тем, что время берётся по факту запроса, а не по времени записи |
| B3. Пул корутин над общей `asyncio.Queue` | N воркеров тянут пары из очереди | равномернее B1 при разбросе латентности | те же проблемы с сессией, что у B1, плюс лишняя механика |

**Выбираю B2.** Это единственный вариант, где вопрос «безопасна ли сессия» не
возникает: конкурентными становятся только `stalcraft_client.get_auction_lots`
(свой `httpx.AsyncClient` на каждый запрос) и `api_cache.set_lots`
(`redis.asyncio` — пул-безопасен). Вся работа с БД, Redis-сигналами и RabbitMQ
идёт как раньше, строка в строку.

**Компромисс, который принимаем:** снапшот пишется до ~10 с позже момента
запроса. Это меньше сегодняшнего разброса (сейчас последний предмет батча
опрашивается на 60-й секунде прогона), поэтому фактическая свежесть только
улучшается. Обязательное условие — `collect_time` и расчёт `hours_remaining`
должны использовать **время запроса** (`fetched_at`), а не время записи.

**Чего сознательно НЕ делаем:**
- не параллелим `_publish_signals` и запись в БД — экономия единиц процентов
  времени ценой потери простоты и безопасности сессии;
- не заводим общий `httpx.AsyncClient` на прогон. Сейчас `client.py:27` создаёт
  клиент на каждый запрос, то есть TLS-хендшейк на каждый вызов — вероятно, 0.2–0.4 с
  из 1.1 с латентности. Это отдельная оптимизация, дающая выигрыш **без единой
  лишней единицы API**, но вносить её вместе с параллелизацией нельзя — станет
  непонятно, что именно дало эффект. Заводим пунктом в `docs/NOTES.md` после того,
  как новый лог (шаг A6) покажет фактическую латентность запроса;
- не трогаем `collect_single_item` (L287) и сигнатуру `_collect_lots_for_item` как
  публичной точки входа — см. §3.9, шаг A2.

### 3.4. Степень параллелизма: 4

Считаем от требования, а не «на глаз». Нужная пропускная способность: батч
`B = 25` пар за время `T ≤ 15 с` (с запасом к такту 20 с) → `1.67 запроса/с`.
По закону Литтла при латентности `L = 1.1 с`: `N = 1.67 × 1.1 ≈ 1.9`.

Берём `N = 4` — двойной запас на «долгий хвост» латентности (один ответ на 3–4 с
не должен растянуть весь прогон) и на рост батча до `MAX_LOTS_PER_RUN = 50`.

Проверка сверху: `N = 4` при паузе 0.2 с внутри воркера даёт мгновенный темп
`4 / (1.1 + 0.2) = 3.1 запроса/с = 6.2 ед/с`. Прогон из 25 пар = 50 единиц за
~9 с; три прогона в минуту = 150 ед/мин — ровно бюджет из §1. Больше 4 брать
незачем: прогон уже укладывается в такт, а расход задаёт круг, а не `N`.

### 3.5. Форма расхода: сериализует ли лимитер параллельные вызовы

`rate_limiter.acquire()` (`core/rate_limiter.py:105-150`) выполняет Lua-скрипт
`_LUA_ACQUIRE` — Redis однопоточен, скрипт атомарен, поэтому **гонки на корзине
нет**: четыре корутины не спишут одну и ту же единицу дважды. Ждать друг друга они
при этом не будут (и не должны).

Чего лимитер **не** даёт — сглаживания. Это token bucket ёмкостью 400: пока в
корзине есть запас, он пропускает всплеск любой формы, а наш минутный счётчик
`stalcraft:requests:minute:<unix_minute>` считает в **фиксированном** окне, тогда
как API — в своём скользящем. Именно это уже давало реальные 429 при счётчике
261/400 (мотивация `FEED_WINDOW_*`, `feed_collector.py:79-97`).

**Оценка риска для нашего случая — низкий, отдельный ограничитель темпа не нужен:**
после ускорения прогон занимает ~9–12 с из 20-секундного такта, то есть расход
watchlist размазан по минуте тремя равными порциями по 50 единиц. Худшее
скользящее окно в 60 с содержит те же три порции = 150 единиц — всплеск **не
усиливается** относительно сегодняшнего состояния, а его пик по секундам
(6.2 ед/с) ниже среднего темпа пополнения корзины (6.67 ед/с).

Поэтому вместо нового механизма: (1) сохраняем паузу `LOTS_REQUEST_DELAY` **внутри
каждого воркера** — это и есть ограничитель темпа; (2) добавляем предохранитель по
фактическому расходу (§3.7); (3) вводим счётчик 429 (Часть B), чтобы гипотеза
«форма расхода безопасна» проверялась фактом, а не рассуждением. Если после
выкатки 429 появятся — вводить общий пейсер (минимальный интервал между
диспатчами), а не уменьшать `LOTS_FETCH_CONCURRENCY` вслепую.

### 3.6. Наложение прогонов и дублирующие обходы

`last_successful_check` проставляется в двух местах: внутри `_collect_lots_for_item`
для «представителя» пары (L419) и в конце прогона — для остальных записей той же
пары (L125–131). Пока прогон не дошёл до пары, она остаётся `due`, поэтому два
одновременных прогона выберут **один и тот же топ очереди** и обойдут его дважды —
двойной расход API без пользы.

Сегодня наложений нет (замер: 511 интервалов, ни одного короче 60 с), но слотов
стало 3, и любой затянувшийся прогон создаёт риск.

| Вариант | Оценка |
|---|---|
| Redis-лок на весь прогон (`SET NX EX`), как `FEED_LOCK_KEY` у ленты | ✅ **выбираю**: 2 обращения к Redis на прогон, шаблон уже есть в проекте (`feed_collector.py:1015-1017`, `acquire_lock`/`release_lock`), покрывает и случай зависшего прогона, который `expires` не ловит |
| Пометка «взято в работу» на каждую пару (ключ на пару, TTL) | 25–50 лишних ключей и round-trip'ов на прогон ради сценария, который лок закрывает целиком; сложнее отлаживать |
| Ничего не делать, полагаться на `expires: 20` | `expires` отбрасывает **непринятый** тик, но не защищает от прогона, который сам идёт дольше такта |

Лок: `watchlist:scan:lock`, TTL 120 с (десятикратный запас к ожидаемым ~12 с; при
падении воркера ключ протухнет сам). Не взяли лок → выходим с `logger.info` и
пометкой `skipped=lock` (нужна для §6).

### 3.7. Предохранитель и взаимодействие с лентой

Лента прерывает цикл, когда общий расход системы выше `FEED_RATE_GUARD_UNITS = 340`
(`feed_collector.py:1510-1519`). Watchlist — приоритетная подсистема (на нём висят
Telegram-сигналы), поэтому его собственный порог обязан быть **выше** ленточного,
иначе первым уступит именно он. Предлагается `WATCHLIST_RATE_GUARD_UNITS = 360`
(90 % лимита) — это не режим работы, а аварийный тормоз против неучтённого роста
(watchlist вырос втрое; стейдж жжёт общий ключ). Реакция — урезать батч вдвое, а
не отменять прогон: полная остановка watchlist хуже, чем замедленный круг.

Проверка «не вытесним ли ленту» — по времени слотов и по единицам:

- **Слоты.** Сейчас прогон занимает слот 61.5 с × 1.6/мин ≈ 98 слот-секунд из 180
  доступных в минуту. После ускорения — 12 с × 3/мин = 36 слот-секунд. Watchlist
  **освобождает** около трети мощности воркера, а не отбирает её.
- **Единицы.** Лента тратит не более 200 единиц за цикл, и длина её цикла
  ограничена собственной последовательной латентностью (100 запросов × ~1.1 с +
  паузы `FEED_REQUEST_DELAY` ≈ 140 с), а не наличием слотов. Значит её средний темп
  остаётся ~86 ед/мин и **не вырастет** от того, что слоты освободились.
  Суммарно ожидаем 150 (watchlist) + ~86 (лента) + история/эмиссия ≈ 240–250 ед/мин —
  ниже её порога 340, ленту не рвём.

Отдельного «бюджета для ленты» внутри watchlist не требуется: роль такого бюджета
играет `WATCHLIST_BUDGET_UNITS_PER_MIN`, ограничивающий батч сверху.

### 3.8. Целевая конфигурация целиком

```
LOTS_REFRESH_INTERVAL          = 20    # без изменений: порог «пора обновить» = такт beat
LOTS_REQUEST_DELAY             = 0.2   # значение то же; теперь пауза внутри воркера
LOTS_FETCH_CONCURRENCY         = 4     # НОВАЯ
TARGET_CYCLE_SEC               = 110   # было 60 (недостижимо при включённой ленте)
MAX_LOTS_PER_RUN               = 50    # без изменений
MIN_LOTS_PER_RUN               = 5     # без изменений
WATCHLIST_BUDGET_UNITS_PER_MIN = 150   # НОВАЯ, кап батча по расходу
WATCHLIST_RATE_GUARD_UNITS     = 360   # НОВАЯ, аварийное урезание батча
WATCHLIST_LOCK_KEY / TTL       = "watchlist:scan:lock" / 120   # НОВЫЕ
beat: schedule = 20 с, expires = 20    # без изменений — теперь осмысленно
```

Формула батча:

```
runs_per_min   = 60 / LOTS_REFRESH_INTERVAL                    # 3
runs_per_cycle = TARGET_CYCLE_SEC / LOTS_REFRESH_INTERVAL      # 5.5
budget_cap     = floor(WATCHLIST_BUDGET_UNITS_PER_MIN / TokenCost.LOTS / runs_per_min)   # 25
batch = max(MIN_LOTS_PER_RUN,
            min(ceil(len(due_pairs) / runs_per_cycle), budget_cap, MAX_LOTS_PER_RUN))
```

Два ограничителя, а не один, сознательно: `TARGET_CYCLE_SEC` выражает намерение
(«хотим круг 110 с»), `budget_cap` — обязательство перед внешним API при росте
watchlist. При 137 парах оба дают 25 — это совпадение сегодняшнего дня, не вечное
свойство.

### 4.2. Где хранить сутки

| Вариант | Оценка |
|---|---|
| **Redis: поминутные ключи расхода с TTL 25 ч + почасовые счётчики отказов** ✅ | **выбираю**: минутный ключ уже пишется атомарно внутри Lua — меняется одно число TTL (`120 → 90000`), новых точек записи для расхода не появляется вовсе. 1440 ключей × ~40 байт ≈ 60 КБ в сутки; чтение окна — один `MGET` |
| Redis: только почасовые агрегаты | экономия 1440 крошечных ключей несущественна, зато теряется **пиковая минута** — а именно она отвечает на вопрос «подошли ли к потолку» |
| Таблица в Postgres | миграция + писатель + чистка + запись в БД на каждый запрос к внешнему API ради операционных данных, ценность которых исчезает через сутки. Overkill |

**Компромисс:** при перезапуске Redis без persistence история теряется. Для
операционного виджета приемлемо; в ответе API отдаём `minutes_observed`, в UI
подписываем, за сколько минут из 1440 есть данные.

**Ключи (все с TTL 90000 с = 25 ч):**

| Ключ | Что | Где инкрементится |
|---|---|---|
| `stalcraft:requests:minute:<unix_minute>` | потреблённые единицы (уже существует) | `_LUA_ACQUIRE`, `rate_limiter.py:73` — меняется только `EXPIRE` |
| `stalcraft:errors:429:hour:<unix_hour>` | реальные отказы API | `client.py:44` перед `raise` |
| `stalcraft:errors:limiter_timeout:hour:<unix_hour>` | наше самоограничение (`TimeoutError`) | `rate_limiter.py:139` перед `raise` |
| `stalcraft:guard_trips:hour:<unix_hour>` | срабатывания предохранителей (лента + watchlist) | `feed_collector.py:1514`, `collectors.py` (шаг A4) |
| `stalcraft:errors:429:last` | ISO-время и путь последнего 429 (строка) | `client.py:44` |

Инкремент — `INCR` + `EXPIRE` одним pipeline, всё в `try/except`, best-effort:
**учёт ошибок не имеет права ломать сбор данных**. В `client.py` на пути 429
переиспользовать переданный `redis_client`, если он есть, иначе создать эфемерное
соединение (путь редкий по определению).

### 4.3. Что показываем и почему

Голое число 429 бесполезно: пока их ноль, панель не отвечает на вопрос «близко ли
мы к потолку». Состав:

1. **429 за сутки** — главный факт (danger при > 0) плюс время последнего.
2. **Пиковый расход за минуту** за сутки и его время — ранний индикатор: 429
   появляются при пике, а не при среднем.
3. **Медиана расхода за минуту** — фон, с которым сравнивают пик.
4. **Срабатывания предохранителей** (лента + watchlist) — «мы сами себя тормозим»:
   в отличие от 429 это значит, что данные не собраны, хотя лимит не нарушен.
5. **Наши `TimeoutError`** от лимитера — та же природа, другая точка отказа.
6. **24 почасовых столбика** (высота = пиковая минута часа, подсветка часов с 429) —
   отвечают «когда», а не только «сколько». Поминутный ряд (1440 точек) в UI **не
   отдаём** — агрегируем на бэкенде.

### 4.4. API: отдельная ручка, а не расширение `/admin/stats`

`GET /admin/stats` (`admin.py:151-208`) вызывается при каждом открытии страницы и
должен оставаться дешёвым. Суточная агрегация (`MGET` на 1440 ключей плюс три по
24) сама по себе недорога, но у неё другая частота обновления и другой смысл.

**Решение:** новая ручка `GET /api/v1/admin/rate-limit/history?hours=24`

## 6. Как замерить результат — до и после (прод)

Снимать **теми же метриками**, что и замер 2026-08-21. Часть B выкатывается первой
именно для того, чтобы пп. 4–5 читались из админки, а не из логов.

| # | Метрика | Как снять | Ожидание после Части A |
|---|---|---|---|
| 1 | Прогонов в минуту | `docker compose -f docker-compose.prod.yml logs worker --since 30m \| grep -c "Collecting lots"`, поделить на 30 | 1.6 → **≈3** (все тики успевают) |
| 2 | Длительность прогона | `... logs worker --since 30m \| grep "watchlist run:"` → поля `fetch_elapsed / persist_elapsed / total` (новая строка, шаг A6) | 61.5 с → **≤15 с**, `fetch_elapsed` ≈ 9 с |
| 3 | Круг обновления предмета | `... logs worker --since 1h \| grep "Watchlist cycle for"` либо SQL ниже (p50/p90) | ~165 с → **105–115 с (p50)**, p90 ≤ 150 с |
| 4 | Счётчик лимитера по минутам | `GET /admin/rate-limit/history` → `peak_units_per_minute`, `median_units_per_minute` | медиана 150 → **≈240**, пик **< 300** |
| 5 | Реальные 429 | `errors_429_total` в той же ручке (+ `grep -c "429 received"` для сверки) | **0** |
| 6 | Дублирующие обходы | SQL ниже | ноль интервалов короче `LOTS_REFRESH_INTERVAL` |
| 7 | Не пострадала ли лента | `... logs worker --since 1h \| grep "feed cycle"` → `units`, `guard_trips`, `items_done`; в админке `guard_trips_total` | `units` ≈ 200 как сейчас, `guard_trips` не растут |

SQL для пп. 3 и 6 (только чтение):

```sql
-- п.3: распределение круга обновления за последний час
WITH g AS (
  SELECT EXTRACT(EPOCH FROM collect_time
         - lag(collect_time) OVER (PARTITION BY item_id, region ORDER BY collect_time)) AS sec
  FROM collected_data
  WHERE collect_type = 'auto' AND collect_time > now() - interval '1 hour'
)
SELECT count(*) AS intervals,
       round(percentile_cont(0.5) WITHIN GROUP (ORDER BY sec)::numeric, 1) AS p50,
       round(percentile_cont(0.9) WITHIN GROUP (ORDER BY sec)::numeric, 1) AS p90,
       round(min(sec)::numeric, 1) AS min_sec,
       round(max(sec)::numeric, 1) AS max_sec
FROM g WHERE sec IS NOT NULL;

-- п.6: дублирующие обходы (интервал короче такта = пара собрана дважды)
WITH g AS (
  SELECT item_id, region, collect_time,
         EXTRACT(EPOCH FROM collect_time
         - lag(collect_time) OVER (PARTITION BY item_id, region ORDER BY collect_time)) AS sec
  FROM collected_data
  WHERE collect_type = 'auto' AND collect_time > now() - interval '1 hour'
)
SELECT item_id, region, collect_time, round(sec::numeric, 1) AS gap_sec
FROM g WHERE sec IS NOT NULL AND sec < 20 ORDER BY sec LIMIT 20;

-- контроль знаменателя формулы §3.2
SELECT count(*) FROM (SELECT DISTINCT item_id, region
                      FROM user_watchlist WHERE is_active) t;
```

Снимать «после» **не раньше чем через 30 минут** после выкатки (минутный счётчик и
`last_successful_check` должны выйти на равновесие) и повторно через сутки — чтобы
поймать взаимодействие с часовыми задачами (`collect_all_history` :00–:11,
`collect_artifact_history` :15).

## 8. Риски

**R1. Общий `client_id` у прода и стейджа (здесь не чиним, но считаемся).**
Прод и локальный/стейдж-стек ходят под одним `STALCRAFT_CLIENT_ID` (3042), но с
разными Redis — два независимых счётчика по 400 на один ключ API. Цифра в админке
и все расчёты §1 **описывают только прод** и являются нижней границей нагрузки на
ключ. Отсюда: (а) бюджет watchlist берём консервативно (150, а не «сколько
влезет»), (б) в UI обязательна подпись из §4.5, (в) в `docs/NOTES.md` — отдельная
задача «развести окружения по ключам API либо по общему счётчику».

**R2. Всплеск на стыке минут.** Наш счётчик — фиксированное окно, у API —
скользящее. Аргумент, почему параллелизация здесь ситуацию не ухудшает, — §3.5
(прогон занимает ~60 % такта, расход остаётся равномерным). Контроль — п. 5 §6.
Если 429 появятся — вводить общий пейсер (минимальный интервал между диспатчами),
а не уменьшать `LOTS_FETCH_CONCURRENCY` вслепую.

**R3. Одна `AsyncSession` в конкурентных корутинах.** Классический способ получить
`InterfaceError` и битые транзакции. Снят выбором B2 (§3.3): в параллельной фазе
нет ни одного обращения к БД. При ревью проверять именно это: в
`_fetch_lots_for_pair` не должно быть ни `db`, ни мутаций `entry`.

**R4. Устаревание данных внутри прогона.** Снапшот пишется до ~10 с позже запроса.
Обязательно передавать `fetched_at` в `_persist_lots_for_item` — иначе поедут
`collect_time`, `hours_remaining` и деление на ликвидные/истекающие лоты.

**R5. Рост watchlist.** Формула батча без капа наращивает расход линейно. Снимается
`WATCHLIST_BUDGET_UNITS_PER_MIN` (§3.8): при росте числа пар деградирует круг
обновления, а не соблюдение лимита. Побочный эффект — свежесть тихо падает,
поэтому фактический круг обязан быть в итоговой строке лога (A6).

**R6. Голодание ленты.** Расчёт §3.7 показывает, что ленте станет **свободнее**
(watchlist освобождает ~60 слот-секунд в минуту), а её собственный темп ограничен
последовательной латентностью, а не слотами. Контроль — п. 7 §6: если `guard_trips`
у ленты начнут расти, первым делом снижать `WATCHLIST_BUDGET_UNITS_PER_MIN`, а не
бюджет ленты.

**R7. Потеря истории при рестарте Redis.** Суточные ключи не переживут очистку
Redis. Принято сознательно (§4.2); в ответе есть `minutes_observed`, в UI — подпись.

**R8. Лок как новая точка отказа.** Зависший ключ `watchlist:scan:lock` остановил бы
сбор целиком. Митигация: TTL 120 с (в 10 раз больше ожидаемого прогона), снятие в
`finally`, явный лог `skipped=lock` — по нему сразу видно, что происходит.
