# ТЗ: Карточка «Ленты» — цены и прибыль по тиру, которым лот прошёл в ленту

## Контекст

Коммит `e497dda` (2026-08-21, ТЗ `docs/tasks/feed-multi-tier-admission.md`) сделал `feed_lots.tier_used`
трёхзначным (`fast` / `normal` / `premium`), а `sell_price_used` — ценой **этого** тира с поправкой на
пачку. Фронтенд под изменение не обновили: карточка предмета, открытая из «Ленты»
(`ArtifactModal` → `LotStatCard` / `MobileLotStatCard` → `useLotStats`), по-прежнему считает, что
бэкенд всегда оценивал лот по тиру `fast`.

Следствие — карточка показывает цены и прибыль **чужого тира**. Расследование проведено
координирующим потоком: расчёт бэкенда воспроизведён вручную по 22 сделкам и сошёлся до рубля,
дефект целиком фронтендовый. Ниже — два конкретных места и одно производное (мобильная подпись).

### Дефект A — `tier_used` захардкожен

`frontend/src/hooks/useLotStats.ts:229`, `feedToSignals`: `tier_used: 'fast'` записан константой,
хотя API отдаёт поле (`FeedLot.tier_used`, `frontend/src/api/feed.ts:72`).

Следствие: флаг `fromBackend` (`useLotStats.ts:434`, условие `sp.label === l.tier_used`) срабатывает
на колонке «Быстро», и прибыль, посчитанная бэкендом для тира `premium`, печатается под этикеткой
«Быстро». Ни в одном месте карточки `tierUsed` сейчас не отображается — пользователь не может
заметить подмену.

### Дефект B — поправка на пачку выводится из цены `fast`

`frontend/src/hooks/useLotStats.ts:404, 414-415`:

```ts
const fastPrice = stats?.sell_options?.find(o => o.label === 'fast')?.price_per_unit ?? null
const factor = isFeed && fastPrice && l.sell_price_used ? l.sell_price_used / fastPrice : 1
```

Формула восстанавливает множитель пачки из оценки бэкенда и верна ровно до тех пор, пока
`sell_price_used` — всегда цена тира `fast`. С трёхтировым допуском у строки тира `premium` она
даёт `PREMIUM_RATIO / FAST_RATIO = 1.06 / 0.94 = 1.12766` — чистый тировый множитель, никакого
отношения к пачке не имеющий. Этот множитель:

- применяется ко **всем трём** ценам тиров (`useLotStats.ts:442`) → все цены завышены на 12.8 %;
- печатается как `batchPricePct` (`useLotStats.ts:448`) → подпись «Цены — для пачки ×1: сделки
  такими пачками идут на 12,8 % дороже штучных» при `amount = 1` и `batch_stats = NULL`
  (`LotStatCard.tsx:457-466`, `MobileLotStatCard.tsx:291-300`).

Правка: брать цену тира `l.tier_used`, а не `fast`. Проверено по бэкенду — направление верное и
полное: `_evaluate_at_tier` (`backend/app/services/analytics/pricing.py:727-760`) считает
`sell_price = option["price_per_unit"] * (bucket_median / normal_price)`, где второй сомножитель
**не зависит от тира** (свойство пачки, знаменатель всегда `normal`). Значит
`sell_price_used / price_per_unit(tier_used)` — это ровно и только поправка на пачку, и применять
её ко всем трём ценам по-прежнему корректно. При `amount = 1` (или отсутствии `batch_stats`)
множитель становится ровно `1`.

Побочная польза: в режиме «Сейчас» множитель, снятый с опорных опций, теперь не тащит в текущие
цены тировое отношение — то есть правка чинит и этот режим, не трогая его код.

### Дефект C (производный от A) — мобильная подпись «прибыль / шт (быстро)»

`frontend/src/components/mobile/MobileLotStatCard.tsx:226-238`: `fastWhatIf` ищется по
`p.label === 'fast'`, а крупное число в режиме «Неделя» берётся из `lot.profit` (оценка бэкенда,
тир `premium`) и подписывается статическим текстом «прибыль / шт (быстро)». Это то самое место,
где чужая этикетка видна буквально. Чинится вместе с A, иначе фикс A останется невидимым на
мобиле.

### Доказательство (прод, 2026-08-21 ~20:15 UTC)

Предмет `qoq6` «Солнце», `qlt=4 ptn=0`, RU. `artifact_variant_stats`: `ref_price = 23 500 000`,
`ref_confidence = medium`, `ref_samples = 22`, `batch_stats = NULL`.
`sell_options`: fast `22 090 000` / normal `23 500 000` / premium `24 910 000`.
`feed_lots`: `amount = 1`, `buyout_per_unit = 22 500 000`, `tier_used = premium`,
`sell_price_used = 24 910 000`, `profit_per_unit = 1 164 500`, `profit_pct = 5.20`.

Карточка показала `24 910 000 / 26 500 000 / 28 090 000` и `+1 164 500 / +2 675 000 / +4 185 500` —
это правильные цены × 1.12766 с этикетками, сдвинутыми на тир вниз. Показанная цена «Выгодно»
(`28 090 000`) выше месячного максимума реальных сделок (`27 000 000`); из 124 сделок за 30 дней по
ней не прошла **ни одна**.

## Изменения по слоям

### Backend

Изменений нет. Проверено грепом, что «всегда fast» на бэкенде не осталось: `evaluate_lot_profit`
вызывается из `market_radar.py:158` и `profitable_lots.py:290` с умолчанием `tiers=("fast",)` —
для них `tier_used` действительно всегда `fast`, это осознанный контракт (watchlist и Радар
отвечают на вопрос «продать быстро»); `tiers=TIER_ORDER` передаёт только `feed_collector.py:545`.
`collectors.py:642` (`predicted_sell_price`) и `monitoring.py:607` — watchlist-ветка, там всё верно.

### Frontend

#### 1. `useLotStats.ts` — `feedToSignals` (дефект A)

`tier_used: 'fast'` → `l.tier_used ?? null`. Комментарий над функцией дополнить одной строкой:
тир приходит с бэкенда и означает «самый быстрый тир, по которому лот прошёл в ленту»
(`pricing.TIER_ORDER`), подменять его константой нельзя — на нём завязан выбор колонки с
бэкендовой прибылью.

#### 2. `useLotStats.ts` — множитель пачки (дефект B)

Внутри `profitableLots`: вместо предвычисленного `fastPrice` брать цену тира конкретного лота:

```ts
const tierPrice = stats?.sell_options?.find(o => o.label === l.tier_used)?.price_per_unit ?? null
const factor = isFeed && tierPrice && l.sell_price_used ? l.sell_price_used / tierPrice : 1
```

Требования к правке:

- Источник цен для множителя остаётся `stats.sell_options` (опорные, 7д), а **не** `sellPrices`
  текущего режима: бэкенд оценивал лот именно против них. В режиме «Сейчас» множитель
  по-прежнему применяется к текущим ценам — поведение не меняем, оно теперь корректнее.
- Тир не найден в опциях (`tierPrice === null`, например строка старого кэша без `tier_used`) →
  `factor = 1`, как и сейчас при `fastPrice === null`. Молчаливый фолбэк, без выдуманных чисел.
- Ветка watchlist (`isFeed === false`) не затрагивается: `factor` там как был `1`.
- Комментарий блока (`useLotStats.ts:396-403`) переписать под новую опору: множитель
  восстанавливается из `sell_price_used / цена тира tier_used`, знаменатель поправки на бэкенде —
  всегда `normal`, поэтому величина тир-независима и правомерно применяется ко всем трём ценам.

#### 3. `useLotStats.ts` — подпись `batchPricePct` только для пачек

```ts
batchPricePct: isFeed && l.amount > 1 && Math.abs(pct) >= 0.1 ? pct : null,
```

Обоснование: бэкенд применяет поправку **только** при `amount > 1 && batch_stats` — при
`amount = 1` любое отклонение `factor` от единицы это дрейф между часовым пересчётом
`artifact_variant_stats` и минутным циклом ленты, а не свойство пачки. Подпись начинается словами
«Цены — для пачки ×N» и при `amount = 1` не имеет смысла ни при каком значении.

Сам `factor` при этом **не** зануляем для `amount = 1`: он держит согласованность
`priceUnit` / `netUnit` / `perUnit` внутри карточки (`netUnit = perUnit + buyPerUnit`), и обнуление
дало бы расхождение в рублях между ценой и прибылью из бэкенда. Гейт ставим только на подпись.

#### 4. `MobileLotStatCard.tsx` — подпись тира (дефект C)

В блоке «Выгодные лоты» (строки 224-238):

```ts
const tier = lot.tierUsed ?? 'fast'
const tierWhatIf = lot.profits.find(p => p.label === tier)?.perUnit ?? 0
const tierLabel = (sellOptions?.find(o => o.label === tier)?.label_ru ?? 'быстро').toLowerCase()
```

Крупное число: `fromBackend ? lot.profit! : tierWhatIf`; подпись — `прибыль / шт ({tierLabel})`.

Регрессий в watchlist нет по построению: там `tier_used` из `/monitoring/signals` всегда `fast`
(умолчание `evaluate_lot_profit`), в фолбеке по `/lots` `tierUsed === null` → фолбэк `'fast'`.
В обоих случаях подпись остаётся «прибыль / шт (быстро)», а число — прежним.

`sellOptions` в компоненте уже деструктурирован (`MobileLotStatCard.tsx:73-76`), новых полей от
хука не требуется.

#### 5. `LotStatCard.tsx` — метка тира у строки (критерий приёмки)

В таблице «Выгодные лоты» три колонки прибыли подписаны `Быстро / Нормально / Выгодно`, но какая
из них несёт число бэкенда — не видно. Добавить в первую ячейку строки (там же, где «выкуп» и
«безубыток», тем же стилем `fs.f11` / `tokens.text2`) строку вида «тир · Выгодно» с тултипом
«Тир, по цене которого лот прошёл в ленту; в его колонке — прибыль, посчитанная сервисом».

Подпись тира берём из `sellPrices.find(p => p.label === lot.tierUsed)?.label_ru` — словарь
карточки (`Быстро / Нормально / Выгодно`), а **не** `feedTierLabel` из `api/feed.ts`
(`Быстро / Нормально / Долго`): смешивать два словаря в одном экране нельзя, расхождение
подписей между лентой и карточкой уже зафиксировано как намеренное (`api/feed.ts:180-197`).

Условие показа: `signalsSource === 'feed' && lot.tierUsed` (проп у компонента уже есть,
`LotStatCard.tsx:81`). В watchlist метка не появляется: там тир всегда `fast`, строка была бы
шумом и изменила бы вид «Избранного» — регрессия по виду недопустима.

Новых токенов/цветов не заводить (`CLAUDE.md`: хекс вне `theme.ts` = дефект).

### Design

Изменений в `design/` нет: метка тира собирается из существующих примитивов строки таблицы
(мелкий текст `tokens.text2` + `Tooltip`), новых компонентов и токенов не появляется.

## Критерии приёмки

Проверяются на лоте из раздела «Доказательство» (`qoq6`, `qlt=4`, `ptn=0`, RU, `amount = 1`,
`buyout_per_unit = 22 500 000`, `tier_used = premium`) — либо на любом живом лоте ленты с
`tier_used != 'fast'` и `amount = 1`, с пересчётом ожидаемых чисел по тем же формулам.

1. Блок «Варианты продажи» в режиме «Неделя» показывает «выставить за»:
   `22 090 000` / `23 500 000` / `24 910 000` — ровно цены `sell_options` варианта, без множителя.
2. Прибыли в тех же трёх карточках: `−1 514 500` / `−175 000` / `+1 164 500`.
   Первые две — клиентский what-if (`цена × 0.95 − 22 500 000`), третья — число бэкенда
   (`feed_lots.profit_per_unit`), и стоит она под «Выгодно», а не под «Быстро».
3. «получишь (−5 %)» у «Выгодно» = `23 664 500` (= `24 910 000 × 0.95` = `perUnit + buyPerUnit`).
4. Подписи «Цены — для пачки ×1…» (`batchPricePct`) нет — ни на десктопе, ни на мобиле.
5. Строка таблицы «Выгодные лоты» несёт метку тира «Выгодно»; колонка «Выгодно» той же строки
   показывает `+1 164 500`, совпадая со строкой ленты и с блоком «Варианты продажи».
6. Мобильная карточка: крупное число `+1 164 500`, подпись «прибыль / шт (выгодно)».
7. Лот с `amount > 1` и непустым `batch_stats` (найти в ленте): подпись `batchPricePct` на месте,
   и `priceUnit` тира `tier_used` совпадает с `feed_lots.sell_price_used` этого лота.
8. Регрессия watchlist: карточка предмета из «Избранного» (десктоп и мобайл) до и после правки
   показывает те же цены, прибыли и подписи; метки тира в строке нет, подпись мобильного числа —
   «прибыль / шт (быстро)».
9. `cd frontend; npm run build` проходит (tsc без ошибок).

## Что НЕ делаем и почему

- **Не переносим поправку на пачку на бэкенд** и не добавляем в `/feed/lots` готовые цены трёх
  тиров. Соблазн есть (клиент восстанавливает множитель делением), но это изменение контракта
  API ради одной строки арифметики, а сама формула уже единственная — второй копии не
  появляется. `CLAUDE.md` Блок 6: точечная правка вместо новой абстракции.
- **Не трогаем `feedTierLabel` / словарь ленты.** Расхождение «Долго» (лента) vs «Выгодно»
  (карточка) — задокументированное решение, а не дефект.
- **Не меняем сортировку и состав «Выгодных лотов».** Порядок и отбор идут с бэкенда, к дефекту
  отношения не имеют.

## Расхождение вероятностей `p_sold_6h` — решение: отдельной задачей, не здесь

Лента считает вероятность по позиции плановой цены в живом стакане
(`FEATURE_POS`, `backend/app/tasks/feed_collector.py:586-604`; на этом варианте 2 живых лота →
страта `thin`) — `p_sold_6h = 32.04 %`, `pct_sold_ever = 40.73 %`. Карточка на тех же данных
берёт страту по отношению цены к опоре (`FEATURE_RATIO`,
`backend/app/services/analytics/pricing.py:565-577`, функция `apply_survival`) — `56 %` и `64 %`.
Разница 25-30 п.п.

**Решение: в это ТЗ не включать, завести отдельной задачей в `docs/NOTES.md`.** Обоснование:

1. Это не фронтенд-дефект и не следствие `e497dda`. Дефекты A/B/C — механические, с
   арифметически проверяемой приёмкой; методологический выбор признака проверяется только
   замером на исторических данных.
2. Правка затрагивает `apply_survival` — общую функцию для **watchlist, Радара и карточки**
   (`item_class` по умолчанию `artefact` именно ради этих путей). Смена признака поменяла бы
   числа во всём приложении, а не только в карточке из «Ленты». Класть такое в багфикс с
   узкой приёмкой нельзя — изменение станет непроверяемым.
3. `FEATURE_POS` требует живого стакана варианта (`ladder` + `rank_for_price`), которого у
   `apply_survival` нет и который для watchlist-путей пришлось бы собирать отдельно. Это
   бэкенд-задача с собственным объёмом, а не строчка в хуке.

**Рекомендация для будущей задачи** (зафиксировать в NOTES, не реализовывать сейчас): источником
истины для карточки, открытой из «Ленты», следует считать `FEATURE_POS` — тот же признак, что у
строки ленты. Он учитывает толщину стакана конкретного варианта, тогда как `FEATURE_RATIO` даёт
одну и ту же вероятность всем вариантам класса с одинаковым тиром (`56 %` у любого `premium`)
и по построению не различает ликвидный вариант и вариант с двумя лотами. Практический путь:
`/feed/variant` уже работает в контексте варианта — передать в `apply_survival` опциональный
`ladder` и при его наличии считать по `FEATURE_POS`, оставив `FEATURE_RATIO` фолбэком для
watchlist/Радара. Перед реализацией — замер: сверить обе оценки с фактическим `outcome`
в `lot_observations`, иначе «источник истины» выбирается по вкусу, а не по данным.
