# ТЗ: сбор наблюдений за лотами (P1-4, фаза A)

**Источник:** `docs/tasks/profit-algo-review.md`, пункт **P1-4** — третий шаг плана.
**Исполнитель:** `backend-dev`.
**Миграции:** нужна одна (новая таблица).
**Бюджет API:** **не затрагивается** — данные уже приходят в сборщике ленты и сейчас выбрасываются.
**Предшествует:** P0-2 (`f4cc106`), P0-1 (`6ede761`), оба на проде.

---

## 1. Почему это отдельная фаза

Разбор описывает P1-4 как «Kaplan—Meier с правым цензурированием». Цензурированные наблюдения — это лоты, которые висели и **не продались**. Проверка показала: таких данных в системе нет и получить их из накопленного нельзя.

**Препятствие 1 — снапшоты обрезаны.** `collectors.py:413` хранит `raw_lots = sorted(lots, key=lot_price_per_unit)[:200]` — только 200 самых дешёвых лотов предмета. Лот исчезает из снапшота не только когда его купили, но и когда его вытеснили более дешёвые новые лоты. Отличить вытеснение от продажи невозможно, а survival-анализ на такой подмене даёт систематически заниженное время дожития.

**Препятствие 2 — лента не хранит историю.** Строки `feed_lots` удаляются, как только лот пропал из скана (`feed_collector.py:584`), плюс уборка осиротевших через `FEED_STALE_ROW_HOURS`. Поле `first_seen_at` есть, но живёт ровно до момента исчезновения — то есть до самого события, которое нужно зафиксировать.

**Препятствие 3 — текущий механизм идёт от продаж.** Вложенная `find_lot_info` в `app/tasks/collectors.py:769-826` берёт сделку из `/history` и ищет её лот в прошлом снапшоте. По построению она видит только тех, кто продался. Отсюда покрытие 25.5 % и ноль наблюдений дольше 48 часов: непроданный лот в `sales_history` не появляется никогда.

Поэтому фаза A — **только сбор**. Кривая, `P_fill(H)` и замена `est_sell_hours` — фаза B, через 1–2 недели накопления. Расчётов на неполных данных в этой задаче не делаем.

---

## 2. Источник данных: только артефакты, только из свипа ленты

Сборщик ленты (`tasks/feed_collector.py`) проходит **полную пагинацию** `/lots` по каждому артефакту (`FEED_MAX_PAGES_PER_ITEM = 10`, до 2000 лотов). Значит для ~103 артефактов он видит стакан целиком, и исчезновение лота — это настоящее исчезновение, а не вытеснение.

**Watchlist как источник не используем.** Там снапшот обрезан до 200 дешёвых (препятствие 1). Записывать оттуда наблюдения нельзя: смесь «продан» и «вытеснен» отравит выборку. Это ограничение зафиксировать в докстринге, чтобы источник не расширили по невнимательности.

---

## 3. Таблица `lot_observations`

Одна строка на лот, а не на наблюдение: момент выставления известен из самого лота (`startTime`), поэтому нужно хранить только факт исчезновения и его причину.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | BigInteger PK | |
| `item_id` | String(50) | |
| `region` | String(10) | |
| `qlt`, `ptn` | SmallInteger | вариант |
| `lot_key` | String(128) | `startTime\|qlt\|ptn\|buyoutPrice\|amount` — уже есть, `feed_collector.py:227-249` |
| `start_time` | DateTime(tz) | выставление, из лота |
| `end_time` | DateTime(tz) | плановое истечение (48 ч), из лота |
| `amount` | Integer | |
| `buyout_price` | BigInteger | цена всего лота |
| `buyout_per_unit` | BigInteger | |
| `ref_price_at_seen` | BigInteger, nullable | **опора варианта на момент первого наблюдения** |
| `first_seen_at` | DateTime(tz) | |
| `last_seen_at` | DateTime(tz) | обновляется каждым циклом, пока лот жив |
| `outcome` | String(12), nullable | `NULL` пока жив; далее `sold` / `expired` / `withdrawn` |
| `resolved_at` | DateTime(tz), nullable | |

Индексы: `UNIQUE (item_id, region, lot_key)`; `(outcome, last_seen_at)` для резолвера; `(item_id, region, qlt, ptn)` для будущей фазы B.

**`ref_price_at_seen` — обязательное поле, не откладывать.** Кривая дожития должна отвечать на вопрос «с какой вероятностью продастся лот, выставленный по цене X относительно опоры». Без опоры на момент наблюдения связать цену с вероятностью задним числом нельзя: опора меняется каждый час, и через неделю мы уже не восстановим ту, что была. Значение берётся из `artifact_variant_stats`, которое сборщик и так держит в руках при скоринге. Может быть `NULL` (вариант ниже пола по P0-2) — это нормально, такие наблюдения в фазе B пойдут только в безусловную кривую.

## 4. Запись

В `feed_collector`, в том же проходе, где сейчас строится `feed_lots` — но для **всех** просканированных лотов, а не только прибыльных. Прибыльность отбирает `feed_lots`; выборка наблюдений обязана быть несмещённой, иначе кривая будет описывать только дешёвые лоты.

Апсерт по `(item_id, region, lot_key)`: новый лот — вставка с `first_seen_at = last_seen_at = now`, уже известный — обновление `last_seen_at`.

**Не удалять исчезнувшие строки.** Пропажа лота из скана — это событие, ради которого таблица и заводится. Резолвер (§5) сам их закроет.

Аккуратно с объёмом одной транзакции: до 2000 лотов на предмет × 103 предмета за полный круг. Писать батчами, как это уже делает `calculate_artifact_variant_stats` (`UPSERT_CHUNK`).

---

## 5. Резолвер исходов

Отдельная периодическая задача, раз в 15 минут. Берёт строки с `outcome IS NULL` и `last_seen_at < now - RESOLVE_DELAY`.

**`RESOLVE_DELAY = 2 часа` — не меньше.** История артефактов собирается раз в час (`collect_artifact_history`, `:15`), поэтому продажа появляется в `sales_history` с задержкой до часа. Резолвить раньше — значит массово помечать проданные лоты как `withdrawn`.

Правила, в порядке проверки:

1. **`sold`** — в `sales_history` есть сделка того же `item_id` / `region` / `qlt` / `ptn` с `total_price == buyout_price` и `amount == amount`, время в `[first_seen_at, last_seen_at + RESOLVE_DELAY]`. Это тот же матч, что в `restore_lot_start` (`collectors.py:793-800`), только с другой стороны.
2. **`expired`** — `end_time <= last_seen_at + допуск на длину цикла`. Лот дожил до конца аукциона и не был куплен. Для survival-анализа это **полное наблюдение** («не продался»), а не цензурирование.
3. **`withdrawn`** — всё остальное: лот пропал раньше `end_time` без подходящей сделки. Продавец снял, либо матч не сработал. Для фазы B это **цензурированное** наблюдение.

Различие пунктов 2 и 3 принципиально: спутать их — значит либо переоценить, либо недооценить вероятность продажи. Поэтому `outcome` хранится тремя значениями, а не флагом «продан / не продан».

## 6. Ретеншен и объём

`LOT_OBS_RETENTION_DAYS = 30` — удалять строки с `resolved_at < now - 30 дней` в существующей ежедневной уборке (`delete_old_data`, 03:00).

**Объём заранее не известен, и это надо измерить, а не угадать.** Верхняя граница — 103 предмета × 2000 лотов = 206 тыс. живых строк; реальное число почти наверняка меньше, но приток новых лотов при жизни лота ≤ 48 ч может дать заметный поток.

Поэтому в задачу входит: логировать на каждом полном круге число вставленных и обновлённых строк, а в резолвере — распределение исходов. **После первых суток снять фактические цифры и сообщить.** Если таблица растёт быстрее ~150 тыс. строк в сутки — остановиться и обсудить прореживание (например, наблюдать только каждый N-й лот варианта), не наращивая ретеншен молча.

## 7. Что НЕ входит

- Расчёт кривой дожития, `P_fill(H)`, замена `est_sell_hours` — **фаза B**, после накопления.
- Любые изменения в `pricing.py`, скоринге ленты, порогах, сортировке.
- Watchlist как источник наблюдений (§2).
- Изменения частоты опроса и бюджета API.

## 8. Критерии приёмки

### 8.1 Тесты

- [ ] Новый лот создаёт строку; повторное наблюдение обновляет `last_seen_at` и **не** плодит дубль.
- [ ] `ref_price_at_seen` пишется из статистики варианта; при отсутствии опоры — `NULL`, без падения.
- [ ] Резолвер не трогает строки моложе `RESOLVE_DELAY`.
- [ ] Матч продажи: совпадение по `total_price` + `amount` + варианту → `sold`.
- [ ] `end_time` в прошлом и нет сделки → `expired`; пропал до `end_time` без сделки → `withdrawn`.
- [ ] Полный `python -m pytest tests -q` зелёный.

### 8.2 На стенде

- [ ] После полного круга свипа таблица заполняется; число строк сопоставимо с числом просканированных лотов.
- [ ] Длительность полного круга ленты **не выросла заметно** (сейчас ~296 с на стенде) — запись не должна душить сбор.
- [ ] Расход API не изменился.
- [ ] Через 2–3 часа после старта: в исходах присутствуют **все три** значения. Если `sold` нет вовсе — сломан матч; если всё `withdrawn` — вероятно, `RESOLVE_DELAY` мал или матч не находит сделки.

### 8.3 Отдельно проверить на проде через сутки

Снять и сообщить: число строк, распределение `outcome`, доля строк с `ref_price_at_seen IS NOT NULL`, суточный прирост. Это вход для фазы B и одновременно проверка, что ретеншен выбран верно.

## 9. Оговорки

- **Наблюдаются только артефакты.** Кривая будет описывать артефактный рынок; переносить её на снаряжение без проверки нельзя.
- **Свип не мгновенный** (~5 мин полный круг, холодные предметы — раз в `FEED_COLD_EVERY_N_CYCLES = 5` циклов). Значит `last_seen_at` знает время исчезновения с точностью до интервала обхода, а для холодных предметов — грубее. Для горизонтов в часы это приемлемо, для минутных — нет; в фазе B считать в часах.
- **`withdrawn` смешивает две причины** — снятие продавцом и несработавший матч. Если доля `withdrawn` окажется высокой (скажем, выше 30 %), это в первую очередь повод проверить матч, а не вывод о поведении продавцов.
