# ТЗ: восстановление жизни лотов из снапшотов (P1-4, стартовый набор)

**Источник:** `docs/tasks/sale-time-prediction-research.md`, `docs/tasks/lot-observations.md`.
**Исполнитель:** `backend-dev`.
**Цель:** получить цензурированную выборку «лот → сколько прожил → чем кончился» **задним числом**, чтобы фаза B не ждала неделю живого сбора.
**Бюджет API:** не затрагивается вовсе — работа только с накопленной БД.

---

## 1. Зачем и почему это вообще возможно

Фазе B нужны оба исхода: продавшиеся и **не** продавшиеся лоты. В `sales_history` вторых нет по построению, а `lot_start` там восстановлен матчингом в окне ~1.7 ч, поэтому среди продавшихся представлены почти только быстрые (медиана 1.02 ч, ноль наблюдений дольше 48 ч). Живой сборщик `lot_observations` эту дыру закрывает, но копит с 2026-08-16.

**Однако история уже есть — в снапшотах.** `collected_data.raw_lots` хранит лоты предмета, и хотя код обрезает список до 200 самых дешёвых (`collectors.py:413`), замер показал, что **обрезка почти не срабатывает**:

| Показатель (замер 2026-08-16, окно 2 ч) | Значение |
|---|---|
| Снапшотов | 3 289 |
| Из них **не обрезаны** (`< 200` лотов) | **3 011 — 91.5 %** |
| Предметов с полным стаканом | **107 из 115** |
| **Из них артефактов** | **59** (из 103 в ленте) |
| Глубина истории | с **2026-06-05**, 6.57 млн снапшотов |

То есть для 59 артефактов доступно ~10 недель полного стакана с шагом ~110 с. Лот, исчезнувший из полного стакана, исчез по-настоящему — а значит различимы продажа, истечение и снятие.

> Замечание к прошлой формулировке: в `lot-observations.md` §2 сказано, что watchlist непригоден из-за обрезки. Механизм существует, но реально срабатывает лишь у 13 предметов из 115 — обоснование было завышенным. Для живого сбора решение всё равно верное (артефакты вне watchlist снапшотов не имеют вовсе), но для **исторического** восстановления источник пригоден.

## 2. Что построить

Разовый скрипт `backend/app/scripts/reconstruct_lot_history.py`, наполняющий **ту же** таблицу `lot_observations` — отдельная схема не нужна, поля совпадают по смыслу.

### 2.1 Алгоритм

Для каждой пары `(item_id, region)` с полным стаканом, по снапшотам в хронологическом порядке:

1. Развернуть `raw_lots` каждого снапшота в множество ключей `lot_key = startTime|qlt|ptn|buyoutPrice|amount` (та же функция, что в сборщике — **переиспользовать, не копировать**).
2. Лот появился (есть в снапшоте `N`, не было в `N−1`) → создать наблюдение: `first_seen_at = collect_time(N)`, поля лота, `queue_rank` / `cheaper_units` / `variant_live_lots` считаются **по этому же снапшоту** (стакан целиком под рукой).
3. Лот пропал (был в `N`, нет в `N+1`) → `last_seen_at = collect_time(N)`, наблюдение закрывается по правилам §2.2.
4. Лот присутствует в последнем доступном снапшоте окна → **цензурировано административно**, `outcome = NULL`. Такие в анализ идут как цензурированные, не как «снят».

### 2.2 Исход

Та же логика, что в `classify_outcome`, включая **расход сделок** (`matched_sale_id`) — иначе воспроизведём баг, который только что чинили:

1. `sold` — есть свободная сделка того же варианта с `total_price == buyout_price`, `amount == amount`, временем в `[first_seen_at, last_seen_at + допуск]`;
2. `expired` — `end_time <= last_seen_at + допуск`;
3. `withdrawn` — остальное.

`matched_sale_id` обязателен: уникальный индекс не даст одной сделке закрыть два наблюдения, но раздача должна быть **детерминированной** (наблюдения от старейшего, сделки от ранней), как в `resolve_batch`.

### 2.3 Пометка происхождения

Новая колонка `source VARCHAR(12) NOT NULL DEFAULT 'live'`, у восстановленных — `'snapshot'`.

**Обязательна:** восстановленные наблюдения имеют другие смещения (см. §4), и фаза B должна уметь их разделять, сравнивать и при необходимости взвешивать. Без пометки два источника необратимо перемешаются.

### 2.4 Опора на момент наблюдения

`ref_price_at_seen` восстановить **нельзя** — опора считается по окну, которое на тот момент было, а `market_statistics` / `artifact_variant_stats` хранят только текущее значение. Оставить `NULL`.

Вместо этого фаза B считает опору сама: по `sales_history` на момент `first_seen_at` тем же `weighted_reference` (данные за 120 дней на месте). Это дороже, но воспроизводимо и одинаково для всей истории. **В скрипт не закладывать** — это работа фазы B.

## 3. Объём и режим работы

Верхняя оценка: 6.57 млн снапшотов × ~150 лотов ≈ 1 млрд пар. В лоб не проходит.

Ограничения, снимающие проблему:
- только предметы, где стакан полный (проверять `jsonb_array_length(raw_lots) < 200` **на каждом снапшоте**, а не по предмету целиком — предмет мог перейти границу);
- только артефакты (`category LIKE 'artefact%'`) — фаза B про ленту;
- окно по умолчанию **30 дней**, параметр `--days`;
- обработка **по одной паре `(item_id, region)`**, стриминг по `collect_time`, в памяти только два соседних снапшота и словарь открытых лотов;
- батчевая вставка, как в `calculate_artifact_variant_stats`.

Скрипт **идемпотентный**: повторный запуск на том же окне не должен плодить дубли — апсерт по `(item_id, region, lot_key)` с сохранением более раннего `first_seen_at`.

**Запускать только вручную**, в beat не добавлять. На проде — с `--days 7` для проверки, затем полное окно.

## 4. Смещения, которые обязаны быть в отчёте скрипта

Их нельзя устранить, но можно измерить и учесть:

1. **Отбор предметов.** 59 артефактов из 103 — те, что кто-то добавил в избранное, то есть заведомо более популярные и ликвидные. Кривая по ним оптимистичнее рынка в целом.
2. **Левое усечение.** Лоты, висевшие на начало окна, входят в середине жизни. Помечать: в основной анализ брать только те, у кого `first_seen_at − start_time` меньше интервала обхода.
3. **Дыры в сборе.** Между снапшотами бывают паузы (рестарты, 429, парковка). Если разрыв больше `MAX_GAP` (предлагаю 15 мин), считать лот цензурированным на последнем наблюдении, а не «снятым» — иначе дыра превратится в фальшивое исчезновение.
4. **Шаг обхода ~110 с** — время исчезновения известно с этой точностью. Для часовых горизонтов приемлемо, для минутных нет.
5. **Обрезка у 13 предметов** — исключаются полностью, не частично.

Скрипт печатает по каждому пункту фактическое число: сколько предметов взято и отброшено, сколько наблюдений левоусечённых, сколько цензурировано по дырам, распределение исходов.

## 5. Критерии приёмки

### 5.1 Тесты

- [ ] Появление/исчезновение лота между двумя синтетическими снапшотами даёт корректные `first_seen_at` / `last_seen_at`.
- [ ] Разрыв больше `MAX_GAP` → цензурирование, а не `withdrawn`.
- [ ] Присутствие в последнем снапшоте окна → `outcome IS NULL`.
- [ ] Одна сделка закрывает ровно одно наблюдение; раздача детерминирована при перемешанном входе.
- [ ] `queue_rank` считается по варианту, а не по предмету.
- [ ] Повторный запуск идемпотентен: число строк не растёт, `first_seen_at` не сдвигается.
- [ ] Полный `python -m pytest tests -q` зелёный.

### 5.2 Проверка совпадения с живым сбором — главный критерий

На окне, где **есть оба источника** (с 2026-08-16), прогнать восстановление и сравнить с `source='live'` по одним и тем же предметам:

| Сверка | Ожидание |
|---|---|
| Доля `sold` / `expired` / `withdrawn` | расхождение в пределах нескольких п.п. |
| Медиана времени жизни проданных | сопоставима |
| Число лотов, увиденных обоими | высокое перекрытие |

**Расхождение в разы означает ошибку восстановления**, а не свойство данных, — в этом случае остановиться и разобраться, не наполняя таблицу.

Это единственная возможность проверить восстановление против эталона, и её нельзя пропускать: живой сборщик пишет полный стакан из ленты и служит здесь истиной.

## 6. Что НЕ входит

- Расчёт кривой дожития, `P(sold ≤ H)`, замена `est_sell_hours` — фаза B.
- Пересчёт `ref_price_at_seen` для восстановленных строк (§2.4).
- Восстановление по снаряжению — только артефакты.
- Автоматический запуск по расписанию.
