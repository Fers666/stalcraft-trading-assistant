**Миграции:** не нужны. Новых колонок нет, изменяются только значения существующих.

## 1. Задача

Опорная цена сейчас считается по любому числу сделок и без защиты от выбросов. Замер на проде 2026-08-14:

- **65 %** обещанной прибыли ленты стоит на 30 лотах, у которых за опорой меньше 5 сделок;
- **509** вариантов помечены `ref_confidence='high'` при `ref_samples < 5` (порог `MIN_REF_SAMPLES = 3` слишком низкий);
- статистических фильтров выбросов нет вообще — только `GLITCH_RATIO`, и тот применяется к аск-фоллбеку, а не к истории;
- ~1 % сделок отклоняются от медианы варианта втрое и более; на выборке из пяти сделок один такой выброс двигает опору ощутимо.

Надо: не выдавать торговый сигнал там, где за оценкой нет данных, а там где данных мало — усаживать оценку к родительскому уровню вместо того, чтобы верить трём сделкам.

## 2. Что меняем

### 2.1 Эффективное число сделок вместо `len(pairs)`

`weighted_reference` уже считает веса `0.5 ** (age_h / 48)`, но в `samples` отдаёт сырой `len`. Три сделки трёхдневной давности дают эффективный вес ~0.9, а не 3 — и это принципиально разные ситуации.

**`backend/app/services/analytics/pricing.py` → `weighted_reference()`** (сейчас `pricing.py:203-236`):
добавить в возвращаемый dict `"weight": sum(w for _, w in pairs)`. Поле `samples` (сырой count) **оставить** — оно уходит в `ref_samples` / `stats_samples` и на него завязан фронт.

### 2.2 Trim выбросов по MAD

> ⚠ **ОТМЕНЕНО Ревизией 1 (§7).** MAD-фильтр схлопывается на круглых ценах. Актуальная редакция — §7.2.

Там же, в `weighted_reference`, **перед** вызовом `weighted_median`:

```python
if len(pairs) >= MAD_MIN_SAMPLES:
    values = [v for v, _ in pairs]
    med = statistics.median(values)
    mad = statistics.median([abs(v - med) for v in values])
    if mad > 0:
        pairs = [(v, w) for v, w in pairs if abs(v - med) <= MAD_TRIM_K * mad]
```

Два предохранителя обязательны:
- `len(pairs) >= MAD_MIN_SAMPLES` — на выборке меньше 8 сам MAD шумит сильнее, чем выбросы, которые он ловит;
- `mad > 0` — у варианта с одинаковыми ценами MAD равен нулю и условие вырезало бы всё, кроме медианы.

`weight` и `samples` считать **после** trim — они описывают то, на чём реально построена опора.

### 2.3 Усадка к родителю

> ⚠ **ОТМЕНЕНО Ревизией 1 (§7).** Усадка снимала пол у 100 % тонких выборок и искажала опору. Актуальная редакция — §7.1.

**`compute_reference()`** (сейчас `pricing.py:239-316`) получает два новых необязательных параметра:

```python
weight:      float = 0.0,          # эффективное число сделок (из weighted_reference)
parent_ref:  Optional[float] = None,   # опора родительского уровня
```

После выбора `ref`/`source` (текущий блок `pricing.py:277-284`), только для источников `weighted_history` / `history`:

```python
if parent_ref and weight < SHRINK_PRIOR_WEIGHT * 2:
    ref = (weight * ref + SHRINK_PRIOR_WEIGHT * parent_ref) / (weight + SHRINK_PRIOR_WEIGHT)
    source = "shrunk_history"
```

Усадка применяется только когда данных мало (`weight < 10`): при толстой выборке она бессмысленна и лишь размывает вариантную специфику.

`ref_source` — `String(20)`, `"shrunk_history"` (14 символов) помещается. Миграция не нужна.

### 2.4 Трёхуровневая уверенность и признак «ниже пола»

В возвращаемом dict `compute_reference`:

```python
"weight":      round(weight, 2),
"confidence":  "high" if weight >= REF_CONF_HIGH_WEIGHT       # 10.0
               else "medium" if weight >= MIN_REF_WEIGHT      # 5.0
               else "low",
"below_floor": weight < MIN_REF_WEIGHT and source != "shrunk_history",
```

`below_floor` — **признак, а не поведение**. `compute_reference` по-прежнему возвращает число: карточка предмета имеет право показать приблизительную оценку с подписью «мало сделок». Решение «не давать сигнал» принимают вызывающие (§2.5).

Значение `"medium"` в `String(10)` помещается.

> **Поправка к первой редакции ТЗ.** Здесь было утверждение «фронт уже умеет три уровня». Оно неверно: `CONF_LABELS` с тремя уровнями в `LotStatCard.tsx:42` применяется к `sell_options.confidence` — **другому полю**. Само `reference_confidence` типизировано как `'high' | 'low'` (`useLotStats.ts:73`), а подпись рендерится только при `=== 'low'`. Рендер от `'medium'` не ломается, но значение молча проваливается, а TS-тип врёт. Правка фронта вынесена отдельно (§6, решение 2).

### 2.5 Гейт в двух скоринговых путях

**Лента** — `backend/app/services/analytics/variant_stats.py` → `compute_variant()` (`variant_stats.py:111-136`):
если `ref_info["below_floor"]` → `ref_price = None` и `sell_options = None`. Дальше вариант уже пропускается скорингом (`tasks/feed_collector.py:368-369`), менять сборщик не нужно.

**Watchlist** — `backend/app/services/profitable_lots.py` (`profitable_lots.py:234-235`):
рядом с `if ref_info is None: return None` добавить `or ref_info["below_floor"]`.

**Карточка предмета и Радар** — гейт **не** применяют, показывают как раньше, но с новым `confidence`.

### 2.6 Откуда берётся `weight` и `parent_ref` в каждом вызове

| Вызов | `weight` | `parent_ref` |
|---|---|---|
| `variant_stats.compute_variant` (`variant_stats.py:110`) | из `wr["weight"]` | опора уровня `(item_id, qlt)` по всем `ptn`, иначе уровня `item_id` по всем `qlt` |
| `profitable_lots`, ветка **с фильтрами** (`profitable_lots.py:215-224`) | из `wr["weight"]` | `stats.reference_price` — опора предмета целиком |
| `profitable_lots`, ветка **без фильтров** (`profitable_lots.py:179-187`) | посчитать `weighted_reference` по `sales_30d` за 7 д — строки уже загружены на `profitable_lots.py:170` | нет: это и есть верх цепочки |
| `market_stats` / `monitoring` (карточка) | из `wr["weight"]` | нет |

**Родительские опоры для ленты считаются бесплатно.** `calculate_artifact_variant_stats` (`variant_stats.py:191-202`) уже держит в памяти все сделки всех вариантов предмета в словаре `groups`. Перед циклом по вариантам собрать два дополнительных словаря — `parent_by_qlt[(item_id, qlt)]` и `parent_by_item[item_id]` — теми же `weighted_reference` по объединённым сделкам, и передавать в `compute_variant`. Дополнительных запросов к БД нет.

### 2.7 Побочная правка: условие записи `reference_price`

`market_stats` пишет `market_statistics.reference_price` только при `source == "weighted_history"` (`market_stats.py:396-398`). После появления `shrunk_history` условие надо расширить, иначе усаженные опоры перестанут сохраняться:

```python
if ref_info["source"] in ("weighted_history", "shrunk_history"):
```

### 2.8 Новые константы

В `pricing.py` рядом с существующими (`pricing.py:30-35`):

```python
MIN_REF_WEIGHT       = 5.0   # эффективных сделок; ниже — below_floor, сигнала нет
REF_CONF_HIGH_WEIGHT = 10.0  # эффективных сделок для confidence="high"
SHRINK_PRIOR_WEIGHT  = 5.0   # вес родительской опоры при усадке
MAD_TRIM_K           = 3.5   # |p - med| > K * MAD -> выброс
MAD_MIN_SAMPLES      = 8     # ниже этого MAD сам шумнее выбросов
```

`MIN_REF_SAMPLES = 3` **оставить** — он продолжает управлять меткой тренда (`pricing.py:290`), это отдельная семантика. За `confidence` он больше не отвечает.

## 3. Критерии приёмки

## 4. Что НЕ входит

Отдельные пункты плана, не трогать в этой задаче:

- квантильные тиры вместо `0.97 / 1.00 / 1.05` — **P0-1**, следующий шаг;
- цензурирование времени продажи — **P1-4**;
- EV-ранжирование и гейт по ликвидности — **P0-3**;
- сторона стакана — **P1-5**;
- починка `signal_outcomes` — **P1-7**.

Здесь меняется **только качество опоры**. Формула прибыли, тиры, пороги маржи и сортировка остаются как есть.

## 5. Отступления от ТЗ, принятые при реализации

**5.1 Центр MAD — взвешенная медиана, а не плоская (§2.2).** С плоской медианой как центром фильтр душит тренд. Замер на регрессе «Юла» (5 дней рынок стоял на 6.8–7.0 млн, последние 2 дня просел до 6.0–6.6): плоская медиана 6.85 млн, MAD 100 тыс, полоса ±350 тыс — **вырезается 8 из 42 сделок, вся свежая просадка**, опора возвращается к несвежему уровню, и фантомная прибыль, ради устранения которой писался `weighted_reference`, возвращается. Со взвешенным центром MAD = 300 тыс, полоса ±1.05 млн: просадка остаётся в выборке, а цель фильтра (отклонения втрое и больше) отсекается по-прежнему. Оба предохранителя §2.2 на месте.

**5.2 Закрыта «усадка к самому себе».** В ТЗ не описана. Если родительская группа состоит из тех же сделок (единственный вариант качества у предмета, либо фильтр покрывает все продажи), усадка ничего не уточняет, но **снимает `below_floor`** — то есть тихо отключает пол. Закрыто требованием, чтобы родительская группа была строго больше своей: в `variant_stats.parent_refs()` и условием `vol < volume_7d` в `profitable_lots`. Покрыто тестами.

**5.3 §2.7 — защитная правка.** `market_stats` не передаёт `parent_ref`, значит `shrunk_history` там появиться не может, и расширенное условие записи пока no-op. Оставлено как защита от регресса при будущих правках.

## 6. Принятые решения по итогам реализации

Три вопроса, всплывшие при реализации; решения приняты пользователем 2026-08-16.

**Решение 1 — хранить эффективный вес честно, а не прокси.** В `monitoring.py`, ветке без фильтров, опора читается из часовой статистики: сырых сделок под рукой нет, а вес в `market_statistics` не хранился. Временно передавался `sales_volume_7d` (сырой count) как заведомо верхняя оценка — уверенность могла быть завышена. **Принято:** добавить колонку `market_statistics.reference_weight` (`Numeric(10,2)`, nullable) и миграцию. Пустой вес у строк, посчитанных до миграции, деградирует в `confidence='low'` — до пересчёта часовой задачей честнее показать «мало данных», чем завышенную уверенность. Гейт `below_floor` карточка не применяет, поэтому сигналы от этого не пропадут.

**Решение 2 — починить фронт.** См. поправку в §2.4: `reference_confidence` типизирован двумя уровнями и не рендерит `'medium'`. **Принято:** расширить тип и показать средний уровень отдельной, более мягкой формулировкой, чем «мало сделок».

**Решение 3 — принять расширенное сокращение сигналов.** По формуле §2.4 источники `history` и `current_fallback` всегда получают `below_floor = True` — эффективного веса у них нет по определению. Значит watchlist перестаёт давать сигналы не только на тонких выборках, но и там, где истории продаж нет вовсе и опора строилась на минимальном аске. **Принято сознательно:** это буквально следует из §1 — не выдавать сигнал там, где за оценкой нет данных. Практическое следствие для замера §3.2: падение числа сигналов watchlist будет шире, чем предсказанное сокращение по «тонким выборкам», и само по себе не является признаком поломки.

## 7. Ревизия 1 — по итогам QA и security (2026-08-16)

Первая редакция ТЗ прошла реализацию (202 теста зелёные), но регрессионное QA на живом стенде показало, что **цель не достигнута и состояние стало хуже исходного**. Обе причины — дефекты проектирования в §2.2 и §2.3, не реализации. Решения по исправлению приняты пользователем.

### 7.0 Что показали замеры

**Гейт `below_floor` не сработал ни разу** — 0 отсечённых из 2434 вариантов:

| `ref_source` / `confidence` | Вариантов | С `ref_price` |
|---|---|---|
| `shrunk_history` / low | 1741 | 1741 |
| `shrunk_history` / medium | 174 | 174 |
| `weighted_history` / high | 519 | 519 |

Строк `weighted_history / low` нет вообще: **каждая** тонкая выборка спаслась усадкой, потому что `parent_ref` нашёлся у 3665 из 3665 вариантов — у любого артефакта есть либо второй `ptn`, либо второе качество.

Последствия: было 65 % обещанной прибыли на тонких выборках → стало **97.4 % на усаженных опорах**. **66.3 % усаженных опор лежат вне всего диапазона реальных сделок варианта за 30 дней**, максимальное завышение **×6.96**. Лента выросла с 370 до 806 строк вместо ожидаемого сокращения.

**MAD-фильтр схлопывается на круглых ценах.** Предохранитель `mad > 0` закрывает только полностью вырожденный случай. Живой пример `wgwz` (qlt 3, ptn 0): 39 сделок, из них **18 по ровно 999 999** → MAD = 1 111, полоса ±3 888 (**0.4 % от цены**), срезано 19 из 39 сделок вместе со всем свежим проливом на 899 999–900 000. По всем вариантам с ≥ 8 сделками: trim сработал на 76.7 %, 27 вариантов провалились под пол исключительно из-за trim, оттуда попали в усадку.

### 7.1 Усадка к родителю удаляется полностью

**Решение:** пол считается только по собственному эффективному весу. Нет 5 эффективных сделок — сигнала нет, точка.

Обоснование: `qlt` / `ptn` — главный ценообразующий признак предмета, поэтому родительская группа через границу качества — **другой товар**, а не уточнение. Ровно это уже зафиксировано комментарием в `profitable_lots.py:200-202` про Магму (145 тыс. против 9.5 млн). Усадка воспроизвела ту же ошибку через `stats.reference_price`.

Лента от этого не схлопнется: на `weighted_history / high` сейчас **367 строк** против **370** до правки — уходит именно мусор.

Удалить:
- параметр `parent_ref` и весь блок усадки в `compute_reference`;
- константу `SHRINK_PRIOR_WEIGHT`;
- источник `"shrunk_history"` (и вернуть §2.7 к исходному условию `source == "weighted_history"`);
- функцию `variant_stats.parent_refs()` и её вызов;
- передачу `parent_ref` в `profitable_lots` (обе ветки).

`below_floor` упрощается до:

```python
"below_floor": weight < MIN_REF_WEIGHT,
```

Этим же снимаются дефекты QA **Д1**, **Д3** и **Д4** целиком.

### 7.2 MAD-trim заменяется отсечкой по кратности

**Решение:** выброс — цена вне диапазона `[med / TRIM_RATIO, med × TRIM_RATIO]`, где `med` — взвешенная медиана.

```python
TRIM_RATIO = 3.0
```

Обоснование: это ровно та величина, которая была измерена в первопричине (`docs/tasks/profit-algo-review.md` §1.7 — 0.38 % сделок выше 3× медианы, 0.60 % ниже ⅓). Критерий свободен от масштаба и от плотности цен, поэтому на круглых ценах не схлопывается.

Предохранители `MAD_MIN_SAMPLES` и `mad > 0` **не нужны и удаляются вместе с MAD**: отсечка по кратности безопасна на любой выборке — на двух сделках `a` и `5a` медиана `3a`, границы `a…9a`, ничего не срезается. Константы `MAD_TRIM_K`, `MAD_MIN_SAMPLES` удалить.

Снимается дефект QA **Д2**.

### 7.3 Подпись уверенности не должна спорить с числом сделок (Д6)

`confidence` считается по эффективному весу, а в подписи печатается сырой `reference_samples`. Локально **48 вариантов** отдают `low` при `ref_samples ≥ 10` — пользователь видит «Мало сделок (29)». Плюс переходный период: пока часовая задача не пересчитала `market_statistics`, `reference_weight = NULL`, и карточка **каждого** предмета покажет эту подпись с любым числом.

Правка фронта: переформулировать обе подписи (`low` и `medium`) так, чтобы текст не противоречил показанному числу — говорить о свежести и глубине выборки, а не о её размере. Файлы — `LotStatCard.tsx:463-472`, `MobileLotStatCard.tsx:300-309`.

### 7.4 Принято сознательно: гейт применяется на записи (Д7)

`compute_variant` обнуляет `ref_price` и `sell_options` прямо в строке `artifact_variant_stats`, а из неё же собирается карточка `/feed/variant`. Значит вариант ниже пола потеряет на карточке цену целиком, а не деградирует в «приблизительно» — это расходится с §2.5, где сказано, что карточка гейт не применяет.

**Принято как есть.** Вариант с менее чем 5 эффективными сделками не имеет цены, которой можно верить, и честнее показать «недостаточно данных», чем число. Строк в `feed_lots` у такого варианта тоже нет, поэтому карточка достижима только переходом «Все лоты предмета». Альтернатива — хранить `ref_price` вместе с флагом в отдельной колонке — потребовала бы ещё одной миграции ради худшего поведения.

### 7.5 Эксплуатационное: миграция строго до выката кода (Д5)

Модель объявляет `reference_weight`, поэтому **любой** SELECT `MarketStatistics` через ORM падает, пока колонки нет. На стенде воспроизведено: `GET /api/v1/monitoring/item/{id}` → 500, `UndefinedColumnError`.

На проде порядок обязателен: `alembic upgrade head` **до** запуска нового образа. Иначе разом лягут карточка предмета, watchlist-задачи и `calculate_market_stats`. Ручки ленты (`/feed/lots`, `/feed/variant`) этой таблицы не касаются и переживут.
