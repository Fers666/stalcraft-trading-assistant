# Прогноз срока продажи: что можно и чего нельзя на наших данных

**Дата:** 2026-08-16. **Статус:** аналитическое исследование, кода не касается.
**Основание:** `docs/tasks/profit-algo-review.md` (P1-4), `docs/tasks/lot-observations.md` (фаза A выкачена), `docs/tasks/quantile-sell-tiers.md` (P0-1), `docs/tasks/ref-quality-floor.md` (P0-2).

---

## 0. Короткий ответ

**Да, прогнозировать срок продажи реально — но не в том виде, в каком он сейчас обещан.**

Три утверждения, на которых стоит всё остальное:

1. **Прогнозировать надо вероятность, а не часы.** Момент покупки — реализация точечного процесса прихода покупателей. Точечная оценка «~2 ч» для отдельного лота не имеет содержания даже при идеальной модели: неустранимая дисперсия сравнима с самой величиной. Прогнозируемая величина — `P(продан ≤ H)` для H ∈ {1, 6, 24, 48}. Ярлыки «быстро / средне / долго» должны быть полосами этой вероятности, а не оценкой часов.

2. **Данные для этого появились ровно 2026-08-16 и раньше их не было.** `lot_observations` — первый в системе источник, который видит **непроданные** лоты. Всё, что построено на `sales_history` (включая нынешний трёхуровневый прогноз), обучено на выборке «те, кто продался» и структурно не может оценить вероятность продажи. Это не недостаток реализации, это отсутствующая величина.

3. **`fill_probability` сейчас измеряет не то, что написано на этикетке** — и это самый крупный логический дефект текущей оценки выгоды, важнее любых калибровок множителей. Разбор — §1.1.

Отдельно: **первые цифры (77.9 % sold / 7.4 % expired / 14.7 % withdrawn) в качестве оценки «доли продающихся лотов» использовать нельзя** — не потому что «мало данных», а по трём конкретным причинам (§2.6). Одна из них систематически завышает `sold` и чинится изменением резолвера.

## 1. Разбор текущей оценки выгоды: логические, а не технические слабости

### 1.1 Главное: `fill_probability` — квантиль цен сделок, а не вероятность продажи

Что измерено (`docs/tasks/quantile-sell-tiers.md` §2): для варианта берутся **цены реально состоявшихся сделок** за следующие сутки, считается их q25 относительно опоры. Получено 0.937 → `FAST_RATIO = 0.94` (`backend/app/services/analytics/pricing.py:52`).

Что заявлено пользователю (`docs/BUSINESS_LOGIC.md:104`, `:123-125`, поле `FILL_PROBABILITY` в `pricing.py:58`): **«шанс продажи ~75 %»**.

Это две разные величины, и вторая из первой не следует:

| | Измерено | Заявлено |
|---|---|---|
| Пространство | сделки, которые **состоялись** | лоты, которые **выставлены** |
| Вопрос | «какая доля прошедших сделок была по цене ≥ X?» | «с какой вероятностью **мой** лот продастся?» |
| Что нужно, чтобы совпало | каждый выставленный лот в итоге продаётся | — |

Последнее условие ложно: по первым же данным `lot_observations` до 22 % лотов закрываются без продажи (`expired` + `withdrawn`). Величина «доля сделок выше цены X» **условна на том, что сделка вообще произошла**, и не содержит информации о частоте прихода покупателей и о числе конкурентов в очереди. Ровно эта разница — цензурирование по факту исполнения — и есть предмет литературы по прогнозу исполнения лимитных заявок ([Lo, MacKinlay, Zhang, JFE 2002](http://web.mit.edu/Alo/www/Papers/JFE2002_Pub.pdf)) и по оценке win-rate в RTB ([Wu et al., KDD 2015](http://www0.cs.ucl.ac.uk/staff/w.zhang/rtb-papers/win-price-pred.pdf)): наблюдаемое распределение цен **выигравших** заявок систематически не равно распределению рынка, и восстанавливать по нему вероятность выигрыша нельзя без модели цензурирования.

Практическое следствие: число 75 в UI — не вероятность ничего. Формулировку надо либо чинить (говорить «цена на уровне 25-го процентиля сделок»), либо подкреплять реальным `P(sold ≤ H)` из `lot_observations`. Второе теперь возможно.

**Дополнительно — калибровочная выборка сама выжившая.** SQL перекалибровки (`quantile-sell-tiers.md` §6) содержит `HAVING count(*) >= 20` на опоре и `HAVING count(*) >= 10` на контрольных сутках. То есть 0.94/1.00/1.06 измерены **только на вариантах с ≥ 20 сделками в неделю и ≥ 10 в сутки**, а применяются ко всем, кто прошёл пол `MIN_REF_WEIGHT = 5.0` (`pricing.py:40`). Оговорка честно записана в §7 ТЗ, но её масштаб не измерен и измерить его старыми данными нельзя — у тонких вариантов не набирается 10 контрольных сделок. `lot_observations` снимает это ограничение: там наблюдение даёт каждый лот, а не каждая сделка.

### 1.2 Срок продажи не зависит от цены самого лота

В ленте `est_sell_hours` берётся из `sell_options` **варианта**, тира `fast`:

```python
hours = (fast or {}).get("estimated_hours")          # feed_collector.py:418
"est_sell_hours": hours,                             # feed_collector.py:441
```

`sell_options` считается один раз на вариант (`variant_stats.py:138-141`). Значит **лот, выставленный на 30 % ниже опоры, и лот по опоре получают одинаковый прогноз времени** — при том, что цена относительно рынка является главным предиктором времени исполнения во всей внешней литературе (у Lo–MacKinlay–Zhang прямо: «execution times are very sensitive to the limit price, but are not sensitive to limit size»).

Это не мелкая неточность: `profit_per_hour_total = profit_total / hours` (`feed_collector.py:440`) — величина, по которой пользователь сравнивает лоты, — делится на число, которое между лотами варианта не меняется вовсе. Внутри варианта сортировка по ₽/час вырождается в сортировку по ₽.

### 1.3 Время не масштабируется размером пачки, а прибыль масштабируется

`evaluate_lot_profit` корректирует **цену** пачки по `batch_stats` (`pricing.py:507-516`), но время оставляет прежним. Затем:

```python
profit_total = evaluated["profit"] * amount                    # feed_collector.py:419
"profit_per_hour_total": round(profit_total / hours, 2)        # feed_collector.py:440
```

Стек из 50 штук получает ₽/час в 50 раз выше одиночного лота при том же `hours`. Продажа 50 штук занимает не то же время, что продажа одной — при `supply_coverage_days`, который система уже считает (`feed_collector.py:327-337`) и не применяет. Дефект отмечен в разборе (P1-4), но он живой и влияет на порядок выдачи прямо сейчас.

### 1.4 Три уровня прогноза — три разные эвристики, ни одна не проверена

| Уровень | Формула | Файл | Природа |
|---|---|---|---|
| 1 (`coverage ≥ 30 %`, ≥10 точек) | среднее по 5 ближайшим по цене парам | `market_stats.py:715-717` | k-NN на цензурированной выборке |
| 2 (`coverage 10–30 %`) | `avg_time × {0.4, 1.0, 2.5}` | `pricing.py:433-436` | множители ниоткуда |
| 3 (`coverage < 10 %`) | таблица по `sales_per_day` | `pricing.py:440-448` | таблица ниоткуда |
| фоллбек | `{fast: 3, normal: 18, premium: 60}` | `market_stats.py:708` | константы ниоткуда |

Все четыре обучены/заданы на парах из `extract_time_price_pairs` (`market_stats.py:532-555`), то есть исключительно на **проданных** лотах, покрытие 25.5 %, ноль наблюдений дольше 48 ч (§1.5 разбора). Выборка не видит ни одного лота, который не продался, — а именно про такие лоты пользователь и хочет знать.

Есть и более тонкий дефект уровня 1: среди **проданных** лотов связь «цена → время» смещена конфаундером. Лот, провисевший долго, продаётся тогда, когда приходит покупатель с высокой готовностью платить; поэтому в выборке проданных дорогие лоты выглядят «медленными» не потому, что цена замедляет продажу, а потому что медленные лоты выживают до дорогого покупателя. Это та же проблема одновременности цены и срока, которая в недвижимости решается системой уравнений и инструментальными переменными ([Haurin et al., Real Estate Economics 2010](https://taylornadauld.com/wp-content/uploads/2025/05/Real-Estate-Economics-2010-Haurin-List-Prices-Sale-Prices-and-Marketing-Time-An-Application-to-U-S-Housing-Markets.pdf)). У нас она мягче (§2.5), но на выборке одних проданных она в полный рост.

### 1.5 Что оценка обещает и что из этого не обеспечено

| Обещание в выдаче | Обеспечено? |
|---|---|
| `profit_pct` — прибыль сделки | Нет. Это валовая наценка **при условии, что продажа состоится по цене тира**. Вероятность этого условия не оценивается. |
| «шанс продажи ~75 %» | Нет. Измерен квантиль цен сделок (§1.1). |
| `est_sell_hours` — срок продажи | Нет. Оценка по продавшимся, не зависит от цены лота (§1.2, §1.4). |
| `profit_per_hour_total` — доходность капитала | Нет. Числитель масштабируется размером пачки, знаменатель нет (§1.3); знаменатель к тому же смещён вниз. |
| `risk` (low/medium/high) | Частично. Это волатильность цены (`classify_risk`, `pricing.py:178-186`), а главный риск здесь — **неисполнение**. Волатильность к тому же считается только там, где сделки были. |

Сквозная логическая ошибка одна: **система оценивает цену, а торговое решение требует пары (цена, вероятность и срок её достижения)**. P0-1 и P0-2 улучшили первую половину; вторая половина отсутствует целиком.

## 2. Прогноз срока продажи: реально ли, какими методами, что применимо

### 2.1 Это задача survival-анализа с конкурирующими рисками, и она стандартна

Целевая величина — время до события с тремя взаимоисключающими исходами. Ровно эта постановка используется:

- **Недвижимость.** [Opendoor, «Liquidity modeling in real estate using survival analysis»](https://www.opendoor.com/articles/liquidity-modeling-real-estate-survival-analysis) — days-on-market как цензурированная величина; листинги, снятые без продажи, и активные листинги входят в обучение как наблюдения без положительных примеров. **Важно для нас: они не строят непрерывную модель дожития, а разворачивают данные в пары «листинг × день» и учат обычный бинарный классификатор «продастся ли в этот день».** Признаки — атрибуты объекта плюс **времязависимые**: текущая цена и **число активных конкурентов**.
- **Недвижимость, конкурирующие риски.** [Copula-based competing risk модель TOM и исхода листинга (JTLU)](https://jtlu.org/index.php/jtlu/article/view/2447) — совместная оценка длительности и типа исхода (продан / снят / переведён в аренду / перевыставлен), с явной корреляцией между длительностью и выбором исхода. Наш случай `sold / expired / withdrawn` — тот же.
- **Биржи.** [Lo, MacKinlay, Zhang, «Econometric models of limit-order executions», JFE 2002](http://web.mit.edu/Alo/www/Papers/JFE2002_Pub.pdf) — AFT-модель с обобщённым гамма-распределением для времени до исполнения лимитной заявки; ковариаты: лимитная цена, размер, спред, волатильность. Отдельно моделируются time-to-first-fill и time-to-completion — прямой аналог «продать 1 шт из стека» против «продать весь стек» (наш §1.3).
- **Биржи, современная версия.** [Deep-LOB: A Deep Learning Approach to Estimating Fill Probabilities in a Limit Order Book (Columbia)](https://business.columbia.edu/sites/default/files-efs/citation_file_upload/deep-lob-2021.pdf) и [Moallemi & Yuan, «A Model for Queue Position Valuation»](https://moallemi.com/ciamac/papers/queue-value-2016.pdf) — вероятность исполнения обусловлена **позицией в очереди и дисбалансом стакана**; эти же признаки стабильно входят в топ информативности.
- **Реклама.** [Wu, Yeh, Chen, «Predicting Winning Price in RTB with Censored Data», KDD 2015](http://www0.cs.ucl.ac.uk/staff/w.zhang/rtb-papers/win-price-pred.pdf) и [Ren et al., «Deep Landscape Forecasting for Real-time Bidding Advertising», KDD 2019](https://arxiv.org/pdf/1905.03028) — win-rate как функция ставки, оценённая по цензурированным данным; DLF явно соединяет дискретную модель хазарда с censored-обучением. [Kaplan–Meier Markov network (Knowledge-Based Systems 2022)](https://www.sciencedirect.com/science/article/pii/S0950705122006219) — индивидуальная KM-кривая на запрос вместо сегментной.
- **Логистика.** [DoorDash, «Improving ETAs with multi-task models, deep learning, and probabilistic forecasts»](https://careersatdoordash.com/blog/improving-etas-with-multi-task-models-deep-learning-and-probabilistic-forecasts/) и [Uber DeepETA](https://www.uber.com/us/en/blog/deepeta-how-uber-predicts-arrival-times/) — принципиальный переход от точечной оценки к распределению/квантилям; у DoorDash отдельно подчёркнуто, что вероятностный слой отделён от слоя принятия решения. Это ровно наша рекомендация «прогноз = вероятность, ярлык = решение».
- **Ритейл/инвентарь.** [Edmunds Days to Turn](https://www.edmunds.com/industry-center/data/days-to-turn.html) — отраслевой стандарт «дней до оборота» как основная метрика ликвидности склада, применяемая для ценообразования.

### 2.2 Что из этого применимо к `lot_observations` — прямо, дёшево, сейчас

Таблица (`backend/app/models/models.py:493-542`) даёт по одной строке на лот: `start_time`, `end_time`, `first_seen_at`, `last_seen_at`, `buyout_per_unit`, `amount`, `qlt`, `ptn`, `ref_price_at_seen`, `outcome`. Этого достаточно для:

**(A) Стратифицированная кривая накопленной заболеваемости (CIF) — «таблица дожития».**
Не Kaplan–Meier в чистом виде, а **cumulative incidence function исхода `sold`** при конкурирующем риске (§2.4). Разрез: децили `buyout_per_unit / ref_price_at_seen` × 3-4 бакета ликвидности варианта × размер пачки. Выход — таблица `P(sold ≤ H)` для H ∈ {1, 6, 24, 48}.
Это **чистый SQL, без ML**, и это правильный первый шаг: он даёт и продукт, и базовый уровень, который любая модель обязана побить.

**(B) Дискретная модель хазарда (подход Opendoor).**
Разворачиваем каждое наблюдение в строки «лот × час жизни» и учим бинарный классификатор `P(продан в этот час | дожил до него)`. Формально корректно и обосновано: [«Survival prediction models: an introduction to discrete-time modeling», BMC Med Res Methodol 2022](https://bmcmedresmethodol.biomedcentral.com/articles/10.1186/s12874-022-01679-6) — дискретное время не требует пропорциональности хазардов, естественно обрабатывает совпадающие времена и позволяет использовать любой классификатор. Даёт бесплатно две вещи, которые нам нужны: **времязависимые признаки** (глубина стакана меняется каждый час) и **возраст лота** как признак.
Объём: при ~58 тыс. лотов/сутки и медианном сроке жизни в часы это порядка миллионов строк «лот-час» за 30 дней — для LightGBM/XGBoost это ничто.

**(C) AFT-бустинг, если хочется прямо срок.**
[Barnwal, Cho, Hocking, «Survival regression with AFT model in XGBoost», JCGS 2022](https://arxiv.org/pdf/2006.04920) — AFT-лосс с поддержкой интервального и правого цензурирования нативно в XGBoost с версии 1.2. Наш случай — **интервальное** цензурирование (событие произошло между `last_seen_at` и следующим несостоявшимся обходом), и XGBoost AFT это поддерживает напрямую. Хорошая вторая итерация, но (A)+(B) закрывают продуктовую потребность.

### 2.3 Признаки: что есть, что дёшево добавить, что не достать

| Признак | Статус | Комментарий |
|---|---|---|
| **Цена относительно опоры** `buyout_per_unit / ref_price_at_seen` | **есть** | Главный предиктор по всей внешней литературе. `NULL` у вариантов ниже пола P0-2 — см. блокер §5. |
| **Позиция в очереди по цене**: сколько единиц варианта выставлено дешевле нас | **восстановимо ретроспективно, но дорого; бесплатно на записи** | Все живые лоты варианта в момент t = строки с `first_seen_at ≤ t ≤ last_seen_at`. Аналог «number of active competitors» у Opendoor и «queue position» в LOB-литературе. **Сборщик держит весь стакан в памяти в `observation_rows` (`feed_collector.py:459-519`) — ранг и глубина считаются там за один проход, ретроспективный self-join по 1.7 млн строк не нужен.** |
| **Глубина стакана дешевле нас (в единицах, не в лотах)** | то же | Важнее числа лотов: 1 лот на 50 шт — не то же, что 50 лотов по 1. |
| **Полный размер стакана варианта / `supply_coverage_days`** | **есть** (считается, `feed_collector.py:327`) | Сейчас только отображается. |
| **Размер пачки `amount`** | **есть** | Ожидаемо снижает хазард; проверить эмпирически, а не постулировать. |
| **`qlt` / `ptn`** | **есть** | Как категориальные, не агрегировать (ошибка №1 из брифа). |
| **Час суток / день недели выставления и наблюдения** | **есть** (из `first_seen_at`) | Заменяет `best_sell_hour` со взвешенным скором `0.6·цена + 0.4·объём` (`market_stats.py:74-96`) — тот скор не оценивает хазард ничем. |
| **Возраст лота** | **есть** | В дискретной модели — базовая ось хазарда. |
| **Тренд варианта 24 ч / 7 д, волатильность** | **есть** (`artifact_variant_stats`) | Но на момент наблюдения не сохранены — только `ref_price_at_seen`. Дёшево добавить по той же схеме. |
| **Медиана живого стакана в момент наблюдения** | **дёшево, на записи** | Нужна как нормировщик цены там, где `ref_price_at_seen IS NULL` (тонкие варианты). |
| **Был ли лот в ленте (наша рекомендация)** | **дёшево** (`feed_lots.lot_key`) | Обязательный признак для честной валидации — см. §3.6. |
| **Ставки/интерес покупателей, просмотры, WTP** | **нет и не будет** | API не отдаёт. Это принципиальный потолок точности. |
| **Личность продавца, история его поведения** | **нет** | Отсюда неустранимая неоднородность в `withdrawn`. |
| **Внутриигровые события (обновления, ивенты, вайпы)** | **нет** | Проявится как необъяснённый сдвиг уровня; ловится переобучением по скользящему окну, а не признаком. |

### 2.4 Три исхода — это конкурирующие риски, и обращаться с ними надо по-разному

`classify_outcome` (`feed_collector.py:577-604`) уже разделяет их правильно, и докстринг фиксирует смысл. Дальше важно не потерять его в фазе B:

- **`sold`** — событие.
- **`expired`** — **полное наблюдение «не продался»**, не цензурирование. Лот дожил до 48 ч и не был куплен. Это самый информативный класс: он прямо говорит «по такой цене рынок не берёт».
- **`withdrawn`** — цензурирование, но почти наверняка **информативное**: продавец снимает лот, потому что тот не продаётся, чтобы перевыставить дешевле. Стандартный KM предполагает независимое цензурирование и на информативном даёт смещение.

Правильный аппарат — CIF при конкурирующих рисках ([обзор методов, arXiv 2212.05157](https://arxiv.org/pdf/2212.05157); [Fine–Gray, практические рекомендации по отчётности, PubMed 28913837](https://pubmed.ncbi.nlm.nih.gov/28913837/)). Практически, поскольку доказать независимость мы не можем, **считать обе границы и показывать разрыв как честную полосу неопределённости**:

```
нижняя оценка: withdrawn = «не продался»       → P(sold ≤ H) занижена
верхняя оценка: withdrawn = цензурирован       → P(sold ≤ H) завышена
```

При нынешних 14.7 % `withdrawn` разрыв порядка 10-15 п.п. — это и есть цена неопределённости, которую нельзя замести. Сузить её можно только детекцией перевыставления (§4.5).

### 2.5 Чего у нас **лучше**, чем в цитируемых системах

Стоит сказать явно, потому что это меняет реалистичные ожидания в хорошую сторону:

1. **Товар внутри варианта однородный.** Артефакт `(item_id, qlt, ptn)` не имеет скрытых атрибутов: в `additional` у артефактов только `qlt` и `ptn` (`pricing.py:119-132`). Значит нет проблемы ненаблюдаемого качества, которая губит недвижимость и eBay и из-за которой там нужны инструментальные переменные. Эндогенность цены сводится к ненаблюдаемой **нетерпеливости продавца** — заметно более слабый конфаундер.
2. **Стакан виден целиком.** Лента идёт полной пагинацией (`FEED_MAX_PAGES_PER_ITEM = 10`, до 2000 лотов). В LOB-исследованиях позиция в очереди часто восстанавливается приближённо; у нас она точная (по цене, а не по времени — на этом рынке приоритет ценовой).
3. **Жизнь лота жёстко ограничена 48 часами.** Административное цензирование справа отсутствует как класс: любое наблюдение закрывается максимум за двое суток. Это редкая роскошь — в недвижимости хвост уходит на годы.
4. **Наблюдается вся популяция, а не отобранная.** `observation_rows` пишет **все** лоты, а не только выгодные (`feed_collector.py:466-472`) — решение уже принято правильно и является ключевым.

### 2.6 Чего в данных не хватает и что прямо сейчас искажает первые цифры

Про 77.9 % sold / 7.4 % expired / 14.7 % withdrawn за первые 3 часа:

**(а) Завышение `sold` из-за неконсумируемого матча.** `classify_outcome` ищет **любую** подходящую сделку и не расходует её (docstring `feed_collector.py:591-594` это признаёт). Однотипные лоты на этом рынке массовы — в разборе P0-2 зафиксирован живой пример `wgwz`: 18 сделок из 39 по **ровно 999 999**. Если по варианту висело 5 одинаковых лотов (цена, количество) и продался один, резолвер пометит `sold` **все пять**. Это не гипотетическая, а количественно измеримая ошибка: сравнить число строк, закрытых как `sold`, с числом различных сделок в окне по тому же ключу `(item, region, qlt, ptn, total_price, amount)`. **Пока это не измерено, доля `sold` — верхняя граница, а не оценка.**

**(б) Левое усечение (delayed entry).** Лоты, уже висевшие на рынке к моменту старта сбора, входят в выборку в середине жизни: `first_seen_at ≠ start_time`. Считать срок как `last_seen_at − start_time` по такой смеси — классическое length-biased sampling: срез живых лотов в любой момент систематически перепредставлен долгоживущими ([обзор смещения при delayed entry, Lifetime Data Analysis 2022](https://link.springer.com/article/10.1007/s10985-022-09562-8); [оценка величины смещения на реальных данных, medRxiv](https://www.medrxiv.org/content/10.1101/2021.08.02.21261492v2.full)).
**Лечится тривиально и полностью:** брать в основной анализ только **инцидентную когорту** — лоты, у которых `first_seen_at − start_time` меньше интервала обхода (то есть мы увидели их с рождения). Начиная с ~2026-08-18 таких лотов достаточно.

**(в) Нестационарность за 3 часа.** Композиция исходов за окно в стационарном режиме несмещена (каждый пришедший лот ровно один раз уходит), но 3 часа — это конкретное время суток. Суточный цикл активности игроков заведомо есть. Нужны полные сутки минимум, неделя — чтобы закрыть день недели.

**(г) `withdrawn` смешивает снятие продавцом и несработавший матч** — оговорка §9 ТЗ. Пока (а) не измерено, разделить их нельзя.

### 2.7 Что не взлетит — прямо

| Идея | Почему нет |
|---|---|
| **Индивидуальная кривая дожития по каждому варианту** | ~900 вариантов с живым стаканом; у тонких — единицы лотов. Пулить надо **по признакам** (цена/опора, глубина, ликвидность), а не по родительскому варианту. Усадка через границу `qlt`/`ptn` уже проверена и провалилась: 66.3 % усаженных опор легли вне всего диапазона реальных сделок варианта (`ref-quality-floor.md` §7.0). Тот же запрет действует и для кривых дожития. |
| **Точечный прогноз «продастся за 2.3 часа»** | Неустранимая дисперсия момента прихода покупателя сравнима с величиной. Даже идеальная модель даёт распределение. `format_hours` (`pricing.py:189-197`) печатает «~2 ч» — ложная точность. |
| **Прогноз с разрешением меньше часа** | Горячие предметы обходятся раз в ~5 мин, холодные — до ~25 мин (`FEED_COLD_EVERY_N_CYCLES = 5`). Время события известно с точностью до интервала обхода. Оговорка §9 ТЗ верна: считать в часах. |
| **Перенос кривой на снаряжение (не-артефакты)** | Наблюдений нет: `lot_observations` пишется только из свипа ленты, а watchlist обрезан до 200 дешёвых лотов (`collectors.py:413`) и как источник запрещён (`models.py:503-508`). Это правильное решение — не отменять. |
| **Разделение «снял продавец» / «сломался матч» без доп. работы** | Требует детекции перевыставления (§4.5) или аудита матчей. |
| **Каузальный ответ «если я поставлю цену X, срок будет Y»** | Наблюдательные данные дают ассоциацию. Смягчающее обстоятельство — однородность товара (§2.5), но нетерпеливость продавца не наблюдается. Единственный чистый путь — эксперимент (выставлять собственные лоты по рандомизированной цене), что вне рамок инструмента. Честная формулировка: «лоты, выставленные по такой цене при такой глубине стакана, продавались за H в N % случаев». |
| **Модель, учитывающая наше собственное влияние на рынок** | При росте числа пользователей лента становится причиной покупок. Пока не измерено — считать пренебрежимым нельзя, но и моделировать нечем (§3.6). |

## 3. Как валидировать, чтобы не обмануться

### 3.1 Целевая метрика

**Основная: калибровка, а не различающая способность.**
Продукт обещает вероятность — значит проверять надо, что заявленные 70 % оказываются 70 %. Конкретно:

1. **Reliability-диаграмма и Brier score для `P(sold ≤ 24 ч)`**, с поправкой на цензурирование (IPCW). Базовый уровень — безусловный CIF. Если модель не бьёт безусловную кривую по Brier — она не нужна.
2. **D-calibration** ([Haider et al., JMLR 2020](https://www.jmlr.org/papers/volume21/18-772/18-772.pdf)) — проверка, что предсказанное распределение осмысленно на всём горизонте, а не в одной точке. Там же аргумент, почему **concordance недостаточен**: C-index измеряет ранжирование и полностью слеп к сдвигу вероятностей. Реализация метрик доступна ([survival_evaluation](https://github.com/haiderstats/survival_evaluation), [mlr3proba dcalib](https://mlr3proba.mlr-org.com/reference/mlr_measures_surv.dcalib.html)).
3. **Time-dependent AUC** — вторичная, для сравнения версий модели между собой.
4. **Решенческая метрика (главная для бизнеса):** на out-of-time данных сравнить два портфеля из топ-N ленты — отсортированный по нынешнему `profit_total` и отсортированный по `EV = P_fill(H) × маржа`. Считать **реализованные ₽ на вложенный рубль в час**, а не обещанные. Это единственное число, которое отвечает «стало ли лучше».

**Взвешивать по вариантам, а не по лотам.** Ошибка №1 из брифа воспроизведётся один в один: 58 тыс. лотов/сутки сосредоточены в нескольких ликвидных вариантах, и метрика, усреднённая по лотам, будет метрикой трёх популярных артефактов.

### 3.2 Разбиение — только временное, и только по группам

- **Walk-forward по календарю:** обучение на днях `t−14 … t−1`, тест на дне `t`, шаг вперёд. Случайное разбиение запрещено: лоты одного варианта в один час делят и опору, и стакан, и покупателя — утечка гарантирована.
- **Группировка при кросс-валидации — по `(item_id, qlt, ptn)`**, иначе тот же вариант окажется в train и test.
- **Замораживать признаки на момент наблюдения.** `ref_price_at_seen` уже заморожен по конструкции (`observation_update_columns`, `feed_collector.py:522-545`) — это правильно и это надо распространить на любые новые признаки. Использовать текущее `artifact_variant_stats` для прошлого наблюдения = утечка из будущего.

### 3.3 Как не обмануться выживанием — чеклист

1. **Никогда не считать метрику только на `outcome = 'sold'`.** Все три исхода и открытые строки должны входить в знаменатель.
2. **Инцидентная когорта в основном анализе** (§2.6б); delayed-entry — только как проверка чувствительности.
3. **Обе границы по `withdrawn`** (§2.4). Публиковать полосу, а не одно число.
4. **Отдельно отчитаться по срезу, где `ref_price_at_seen IS NULL`.** Это тонкие варианты — то есть ровно те, где прогноз важнее всего и где его качество будет худшим. Скрыть их в среднем — повторить ошибку с 509 вариантами `high` на трёх сделках (§1.4 разбора).
5. **Отбраковать строки с `last_seen_at > resolved_at`** — механика уже предусмотрена в докстринге `observation_update_columns`.
6. **Проверить долю коллизий матча (§2.6а) до любых выводов.** Это блокирующая проверка.

### 3.4 Как не переобучиться

- Признаков должно быть единицы, а не десятки. Априорно ожидается, что **ранг по цене в стакане и цена/опора дают почти весь сигнал**; проверка гипотезы «модель бьёт двумерную таблицу» — главный тест на нужность ML вообще.
- Лестница базовых уровней, ниже которой нельзя опускаться при отчёте:
  `(0)` нынешняя эвристика → `(1)` глобальный CIF → `(2)` CIF по децилям цена/опора → `(3)` + бакет ликвидности → `(4)` дискретная модель хазарда.
  **Внедрять простейшее, которое выигрывает.** Если `(2)` не проигрывает `(4)`, надо выкатывать `(2)` — таблицу, а не модель.
- Прогонять переобучение по скользящему окну (раз в неделю) и следить за дрейфом, а не считать модель один раз. Предупреждение о переобучении бэктестов на игровых рынках уже стоит в источниках разбора ([EVE Market Strategies](https://orbitalenterprises.github.io/eve-market-strategies/index)).

### 3.5 Когда данных станет достаточно

| Что | Когда |
|---|---|
| Первая полная инцидентная когорта (48 ч жизни + 2 ч резолва) | **~2026-08-18, вечер** |
| Полная неделя (закрыт день недели) | ~2026-08-23 |
| Две недели — рабочий датасет для `(2)`–`(4)` | **~2026-08-30** — совпадает с планом фазы B из ТЗ |
| Ограничение сверху | `LOT_OBS_RETENTION_DAYS = 30` (`feed_collector.py:138`) |

### 3.6 Обратная связь инструмента на рынок

Лента говорит пользователям, что покупать. Купленные лоты исчезают быстрее → модель, обученная на `lot_observations`, частично учит поведение **собственного продукта**. Это стандартная проблема логированной обратной связи в рекомендательных системах.

Минимальная защита стоит копейки: `feed_lots.lot_key` совпадает с `lot_observations.lot_key`, поэтому признак «лот был в ленте» — один join. Дальше:
- включить его в модель как признак и **смотреть на его вес** — это прямая оценка размера эффекта;
- при оценке качества сравнивать метрику на «был в ленте» и «не был».

Побочная польза: тот же джойн отвечает на самостоятельно ценный вопрос — **действительно ли лоты из ленты уходят быстрее сопоставимых нелент**. Это первый в системе честный ответ на «работает ли инструмент».

## 4. Что ещё можно извлечь из имеющихся данных

Отсортировано по отношению польза/стоимость.

### 4.1 Настоящий fill rate тиров — проверка того, что уже выкачено 🔥

**Польза: максимальная. Стоимость: один SQL-запрос.**
Взять инцидентные наблюдения, сгруппировать по `buyout_per_unit / ref_price_at_seen` вокруг 0.94 / 1.00 / 1.06 и посчитать долю `sold` за 24 и 48 ч. Это **прямая проверка утверждения «шанс продажи 75 %»** (§1.1), которое сейчас показано пользователю и никогда не измерялось. Результат либо подтверждает подпись, либо требует её переписать — и то и другое ценно немедленно.

Заодно закрывает и вопрос из `quantile-sell-tiers.md` §7: как ведут себя тонкие варианты (5-20 сделок), которые измерить по сделкам было невозможно. По лотам — возможно.

### 4.2 Диагностика матча резолвера 🔥

**Польза: блокирующая. Стоимость: один запрос.**
Коллизии `sold` (§2.6а) и доля `withdrawn` по вариантам. Без этого числа любые выводы из `lot_observations` условны. Если коллизии значимы — резолвер надо научить расходовать сделки (или хотя бы ограничивать число `sold` на сделку), и это правка в 20 строк.

### 4.3 Кривая «цена → вероятность продажи» вместо трёх магических множителей

**Польза: высокая. Стоимость: SQL + правка `make_sell_options`.**
Сейчас `{0.4, 1.0, 2.5}` (`pricing.py:434-436`) — числа ниоткуда. По наблюдениям строится настоящая кривая `P(sold ≤ H | цена/опора)`, и три тира становятся тремя точками на ней с **измеренными** вероятностями. Это и есть содержательное завершение P0-1: тир перестаёт быть множителем и становится выбором точки на кривой компромисса цена/срок — ровно тот объект, который в недвижимости называется price–TOM trade-off ([Springer, JREFE](https://link.springer.com/article/10.1023/A:1021526332732)).

### 4.4 Ликвидность по несостоявшимся продажам вместо `sales_per_day`

**Польза: высокая. Стоимость: агрегат по таблице.**
`expired`-доля варианта — прямой, наблюдаемый измеритель «рынок не переваривает». Сейчас ликвидность оценивается через `sales_per_day` (`variant_stats.py:154`) — величину, которая по построению видит только успехи. Гейт по ликвидности, которого требует P0-3, гораздо честнее строить на `expired`-доле и на отношении «пришло лотов / продалось лотов» за сутки.

### 4.5 Детекция перевыставления

**Польза: высокая (разводит `withdrawn` на две причины). Стоимость: средняя.**
`lot_key = startTime|qlt|ptn|buyoutPrice|amount` (`feed_collector.py:248-270`), поэтому перевыставленный лот — это новая строка с новым `start_time`, тем же вариантом и тем же `amount`, появившаяся вскоре после закрытия предыдущей, обычно с более низкой ценой. Эвристика несовершенна, но она превращает `withdrawn` из мусорной корзины в сигнал «продавец сдался и снизил цену» — а это и есть механизм, из-за которого цензурирование информативное (§2.4). Дополнительный бонус: цепочки перевыставлений дают прямое наблюдение **скорости уступки рынка**.

### 4.6 Распределение асков, а не только сделок

**Польза: высокая. Стоимость: низкая (данные уже лежат).**
Опора строится только по **исполненным** сделкам (`weighted_reference`, `pricing.py:253-293`). Это в точности censored-observation problem из RTB: наблюдаются только выигравшие ставки. `lot_observations` содержит **все** аски, в том числе никогда не исполнившиеся. Из них восстанавливается полное распределение готовности продавать и, главное, детектируются варианты, где весь стакан стоит заметно выше опоры (там опора описывает прошлое, а не достижимое).

### 4.7 Час суток по хазарду, а не по взвешенному скору

**Польза: средняя. Стоимость: низкая.**
Заменить `weighted_score` с весами `0.6 цена + 0.4 объём` (`market_stats.py:74-96`, число «60/40» ничем не обосновано) на измеренный почасовой хазард продажи. Побочно закрывает P2-10: `best_sell_hour` начинает участвовать в решении, а не украшать карточку.

### 4.8 Кривая по размеру пачки

**Польза: средняя. Стоимость: низкая.**
`amount` есть в каждом наблюдении. Прямо измеряется, во сколько раз медленнее продаётся стек — то, чего сейчас не хватает для §1.3. Аналогия из LOB — раздельные модели time-to-first-fill и time-to-completion у Lo–MacKinlay–Zhang.

### 4.9 Честная замена `signal_outcomes` (P1-7)

**Польза: высокая, но зависит от 4.2. Стоимость: средняя.**
`evaluate_signal_outcomes` (`backend/app/tasks/analyzers.py:264-307`) ищет любую сделку предмета в полосе ±15 % и даёт 99.5 % «продано». `lot_observations` уже содержит правильный примитив — конкретный лот и его исход. Метрику надо переносить туда, а не чинить старую.

### 4.10 Архив агрегатов перед ретеншеном

**Польза: низкая сейчас, растёт со временем. Стоимость: минимальная.**
`LOT_OBS_RETENTION_DAYS = 30` удаляет сырьё. Перед удалением стоит складывать суточный агрегат (CIF по стратам) в маленькую таблицу — тогда через полгода можно будет отвечать на вопросы о дрейфе рынка, а не начинать с нуля.

## 6. Рекомендуемый порядок

1. **Немедленно, без ожидания данных:** §4.2 (диагностика матча) и блокер №3 (ранг/глубина/медиана стакана на записи). Оба дешёвые, второй — с каждым днём ожидания теряется история признака.
2. **~2026-08-19,** на первой инцидентной когорте: §4.1 — проверка настоящего fill rate тиров. Ответ на вопрос «правда ли 75 %» получаем через трое суток после старта сбора.
3. **~2026-08-30,** фаза B: CIF по стратам (уровень `(2)` лестницы §3.4), обе границы по `withdrawn`, отчёт по срезам. Замена `est_sell_hours` на `P(sold ≤ H)` в API и UI.
4. **После этого** — дискретная модель хазарда, но **только если она бьёт таблицу** по IPCW-Brier на walk-forward.
5. **Параллельно** — переформулировать `fill_probability` в UI (§1.1): это правка текста, она не ждёт никаких данных и убирает утверждение, которое сейчас не соответствует измеренному.
