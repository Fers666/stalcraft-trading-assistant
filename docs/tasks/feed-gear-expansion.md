# ТЗ: расширение «Ленты» на снаряжение, части предметов, премиум и сезонные пропуска

**Статус:** план утверждён пользователем; прод-проба выполнена 2026-08-17
**Предшественники:** `artifact-feed.md` (Ф7), `sale-survival-curve.md` (P1-4 фаза B),
`ev-ranking.md` (P0-3), `audit-on-auction-status.md` (признак торгуемости)

---

## 1. Задача

Лента видит только артефакты — маска `category LIKE 'artefact%'` зашита в шести местах.
Расширить набор на снаряжение высоких рангов, все «части предметов», премиум-статусы и
сезонные пропуска.

Признак торгуемости, на котором строится отбор, в системе уже есть: `master_items.on_auction`,
заполнен задачей `audit_auction_status` реальной пробивкой через Stalcraft API.
Качество ветеран/мастер/легенда — это `master_items.color` ∈
`rank_veteran` / `rank_master` / `rank_legend`.

**Ключевое отличие снаряжения от артефактов:** у не-артефактов в лоте нет `additional.qlt` —
качество является свойством предмета из каталога. `pricing._COLOR_TO_QLT`:
`rank_veteran`→3, `rank_master`→4, `rank_legend`→5.

## 2. Набор предметов (прод-замер 2026-08-17)

Предмет входит в ленту, если `on_auction IS TRUE` **и** выполнено любое из правил:

| Правило | Кандидатов | Торгуется |
|---|---|---|
| `category LIKE 'artefact%'` (как сейчас) | 104 | **103** |
| `category LIKE 'weapon%'` + ранг ∈ {veteran, master, legend} | 249 | **111** |
| `category LIKE 'attachment%'` + те же ранги | 137 | **68** |
| `category LIKE 'armor%'` + те же ранги | 75 | **33** |
| `category LIKE 'backpacks%'` + те же ранги | 10 | **2** |
| `name_ru ILIKE 'Часть%'` — все ранги, включая default | 123 | **55** |
| `name_ru ILIKE 'Премиум на %'` | 9 | **7** |
| `name_ru ILIKE 'Сезонный пропуск%'` | 3 | **3** |

**Итого 382 предмета** против 103 сегодня (+279).

Замер подтвердил: чем выше ранг, тем реже предмет торгуется (weapon — newbie 72 %,
stalker 70 %, veteran 49 %, master 38 %; armor master — 19 %; attachment legend — 0 из 5).
Это не дефект отбора, а свойство рынка: высокотировая экипировка получается апгрейдом,
а не покупкой (`audit-on-auction-status.md`, гипотеза A подтверждена пользователем на АК-103).

Правила не свести к одному предикату по рангу: премиум и сезонные пропуска лежат в
категории `other`, а там 361 предмет с рангами veteran/master/legend — почти сплошь
косметика (облики ZIVCAS, скины, эмоции, клички). Поэтому ранговое правило действует
внутри категорий снаряжения, а премиум и пропуска заданы шаблонами имени. Сезонные
пропуска в любом случае требуют явного правила: они пришли разовым импортом
(`import_arsenal_items.py`) с `color = NULL`.

**Фильтр торгуемости — строгий `on_auction IS TRUE`**, а не `IS NOT FALSE` как сейчас
(`feed_collector.py:1159`). Предмет с `FALSE`/`NULL` не даст ни одной строки, а бюджет
на его опрос потратится. Следствие: новые предметы после `refresh-catalog` приходят с
`on_auction = NULL` и в ленту не попадут, пока вручную не дёрнуть
`POST /admin/audit-auction-status` — задокументированное поведение (`NOTES.md:341`).

**Не входит в объём:** передаваемого «уровня сезона» в каталоге нет вообще, его `item_id`
не нашёлся ни в одном источнике (`arsenal-items-verification.md` §2A). Поиск id — отдельная
задача.

## 3. Backend

### 3.1 Единый scope — новый `backend/app/services/feed/scope.py`

Константы `FEED_GEAR_CATEGORIES`, `FEED_RANKS`, `FEED_NAME_PATTERNS` + функция
`feed_scope_clause()`, возвращающая SQLAlchemy-предикат по `MasterItem`, и
`feed_item_class(category)` → `"artefact" | "gear"`.

Заменить маску `artefact%` у всех потребителей:

- `feed_collector.py:1146-1163` — `_artifact_items()` → `_feed_items()`
  (вызывается дважды: строки 1233 и 1504);
- `variant_stats.py:193` — набор для пересчёта вариантов;
- `feed.py:689,697` — `sales_24h` / `items_tracked` в `/feed/summary`;
- `backfill_artifact_history.py:46-58` — `_find_items()`;
- `reconstruct_lot_history.py:83,337` — `ARTEFACT_CATEGORY`.

Правило не дублировать нигде больше — иначе списки разъедутся, как уже разошёлся
`_SINGLE_CATEGORIES` между парсером и фильтром каталога.

### 3.2 Качество не-артефактов — самый опасный участок

**Обязательный пункт, не улучшение.** Сейчас лента вызывает
`_lot_quality_enchant(lot, None, True)` в пяти местах: `feed_collector.py:278, 391, 403,
554, 668`. Аргументы `master=None, is_art=True` допустимы ровно потому, что набор
гарантированно артефактный — на строке 390 это прямо написано комментарием.

Для снаряжения ломается **дважды**, причём второй раз молча:

1. `pricing._lot_quality_enchant` для не-артефакта берёт качество из `master.color`,
   а `master` передаётся `None`;
2. **рассинхрон ключа варианта.** `variant_stats.variant_key()` (`variant_stats.py:53-67`)
   берёт `(qlt, ptn)` из `additional_info` продажи с дефолтом 0. У снаряжения `additional`
   не содержит ни `qlt`, ни `ptn` — все продажи ветеранского ствола сложатся в вариант
   `(0, 0)`, тогда как сборщик посчитает качество из `color` = 3 и пойдёт искать `(3, 0)`.
   `_load_variants()` промахнётся, `score_item_lots()` не найдёт `ref_price`, и лента по
   снаряжению **вернёт ноль строк без единой ошибки в логах**.

Лечение: общий резолвер качества, принимающий `additional_info`/`lot` и `MasterItem`,
с фолбэком на `_COLOR_TO_QLT`. Используется и `variant_key()`, и `_lot_quality_enchant()` —
обе стороны обязаны давать один ключ. `MasterItem` в сборщике уже под рукой.

### 3.3 Кривая дожития — измерение класса

Механику менять **не нужно**: `MIN_STRATUM_N = 200` уже обеспечивает «выкатить и набирать
данные, прогноз уточняется». Страта не публикуется, пока не наберёт 200 наблюдений, пустая
`SurvivalTable` — штатное состояние (`survival.py:137-141`), пересчёт полный раз в сутки.

Требуется ровно одно: **добавить измерение `class` (`artefact` / `gear`)**, чтобы снаряжение
не заимствовало артефактную кривую.

- миграция: колонка `class` в `sale_survival`, уникальный ключ →
  `(class, feature, bucket, horizon_h)`; существующие строки → `'artefact'`;
- `survival.py`: `class` в `GROUP BY` `_AGG_SQL` (через `JOIN master_items` по `item_id`),
  в `_stratum_row()`, в ключ `SurvivalTable._rows`, в сигнатуры `get()` / `summary()`.
  **Осторожно:** `_AGG_SQL` теперь собирается через `.replace("{known}", _KNOWN_AT_H)`
  (`survival.py:246`) — при правке не сломать подстановку;
- `pricing.apply_survival()` / `make_sell_options()` — принимают класс и прокидывают его;
- `feed_collector._scenario()` (внутри `score_item_lots`) — вызывает
  `survival.summary(FEATURE_POS, bucket)` и `survival.get(...)`, обе сигнатуры меняются;
- `test_sql_buckets_match_python` (`test_sale_survival.py:122`) — расширить на новое
  измерение.

Классов ровно два: `artefact` и `gear` (всё не-артефактное в наборе, включая части и
премиум). Дробить мельче нельзя — страты не наберут `MIN_STRATUM_N`. Осознанный компромисс,
при накоплении данных можно пересмотреть.

**Поведение после выкатки:** gear-страт нет → `get()` возвращает `None` → потребитель
деградирует так же, как артефакты до первого пересчёта. Дальше страты появляются по одной
и уточняются каждые сутки. Второй выкатки не нужно.

Наблюдения по снаряжению пишутся тем же кодом (`feed_collector.py`, запись
`LotObservation`), как только предметы попадут в набор — правок не требует.

### 3.4 Следствие для ранжирования (новое, после P0-3)

Лента сортируется по `ev_profit` (`feed.py:455`), а `ev_profit = NULL`, когда вероятность
не измерена, и такие строки уходят в конец (`nulls_last`, `feed.py:402`). Пока gear-страты
не набрали 200 наблюдений, **всё снаряжение будет лежать хвостом под артефактами** в режиме
«Все». Порядок не ломается — `profit_total` стоит вторичным ключом ровно на этот случай, —
но снаряжения фактически не видно.

Поэтому **серверный фильтр по категории (§3.5) обязателен к выкатке вместе с набором**,
а не после: при выборе чипа «Оружие» выдача целиком из снаряжения и `nulls_last` не вредит.
Подставлять `p = 1` для снаряжения запрещено — это ровно то допущение «продастся
обязательно», ради снятия которого делался P0-3.

### 3.5 API `/feed/lots` — параметр `category`

Сейчас параметра нет (`feed.py:452-458`): фронт эмулирует группы через `item_id[]`, список
капнут `FEED_MAX_LIST_VALUES = 50`. На 382 предметах механизм ломается физически.

Добавить `category: list[str]` с группами из scope-модуля; `/feed/filters` — отдавать
счётчики по новой таксономии.

### 3.6 Опоры цен: разовый бэкфилл истории

`ref_price` считается из `sales_history` за 30 дней (`variant_stats.py:182-197`). По
снаряжению истории в базе нет — без опор `score_item_lots()` отбракует все лоты.

Нужен прогон `backfill_artifact_history.py` (после обобщения набора в §3.1) по новым
предметам. Скрипт **уже имеет** встроенную оценку стоимости (`_estimate()`, лёгкий
`limit=1` на предмет) и просит подтверждения перед основным проходом — угадывать бюджет
не нужно. Суммарная история новых групп ~8.1 млн записей против 48.3 млн у артефактов,
то есть проход заметно дешевле уже пройденного артефактного.

**Запускать только после явного подтверждения пользователя.**

## 5. Бюджет API

**Вписаться в текущий `FEED_BUDGET_UNITS_PER_MIN = 200`.** Лимит 400/мин и параметры
watchlist не трогать. Менять `FEED_BUDGET_UNITS_PER_MIN` / `LOTS_PER_RUN` / `BATCH_SIZE` /
`REFRESH_INTERVAL` — только с отдельного разрешения пользователя (CLAUDE.md Блок 4).

Правок планировщика не требуется: `plan_run()` берёт предмет целиком или не берёт
(`feed_collector.py:229-247`), `select_by_tempo()` пускает холодные предметы раз в
`FEED_COLD_EVERY_N_CYCLES = 5` циклов, предохранитель `FEED_RATE_GUARD_UNITS = 340`
прерывает цикл при перерасходе. Превысить лимит сборщик не может конструктивно —
худшее следствие расширения набора — растянутый интервал обновления **для всего**,
включая артефакты.

Заранее оценить расход пагинации нельзя: `lots_total` в каталоге почти везде `NULL`,
потому что `audit_auction_status` по дизайну не спрашивал `/lots`, если история непустая.
Замерить фактический цикл и расход после выкатки — в `NOTES.md:304` для этого уже заведён
пункт «Калибровка сборщика ленты после первого прогона».

## 6. Критерии успеха

- [ ] `feed_scope_clause()` — единственный источник правила; `grep 'artefact%'` по backend
      не находит дублей набора вне `scope.py`.
- [ ] Юнит-тест резолвера качества: ветеранский ствол даёт `qlt = 3` и из лота
      (`additional` пустой, `color = rank_veteran`), и из продажи; `variant_key()` и
      `_lot_quality_enchant()` возвращают один ключ. Прямая защита от «лента молча пустая».
- [ ] Миграция `sale_survival.class` применяется и откатывается; существующие строки
      получили `'artefact'`; `test_sql_buckets_match_python` расширен и зелёный.
- [ ] `recalculate_survival()` на данных обоих классов не смешивает страты.
- [ ] Существующие тесты (`test_feed_scoring.py`, `test_sale_survival.py`,
      `test_feed_budget.py`, `test_pricing.py`) зелёные.
- [ ] После бэкфилла у снаряжения появились `artifact_variant_stats` с `ref_price`;
      `GET /feed/lots?category=weapon` возвращает непустой список.
- [ ] `GET /feed/filters` отдаёт новые группы со счётчиками; чипы фильтруют серверно.
- [ ] У строк снаряжения до накопления страт `ev_profit` и колонки прогноза пустые,
      а не нулевые и не артефактные; сортировка не разваливается.
- [ ] Прогон на проде: суммарный расход `get_consumption_stats` < 400/мин, всплеска 429
      нет, watchlist-цикл не деградировал.
- [ ] Сезонные пропуска (`g49mp`, `zz02n`, `5l6n0`) и торгуемый премиум видны в ленте.
