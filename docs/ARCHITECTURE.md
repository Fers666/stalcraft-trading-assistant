# Архитектура сбора данных

## Проблема наивного подхода

Если хранить сбор данных **per-user**, при росте числа пользователей возникает катастрофическое дублирование:

```
100 пользователей × 50 товаров в watchlist = 5000 пар (item_id, region)
5000 × 2 запроса = 10 000 запросов за один цикл сбора → лимит 400 запросов/мин → НЕВОЗМОЖНО
```

Также нет смысла собирать данные по одному `(item_id, region)` 100 раз —
рыночные данные одинаковы для всех пользователей.

---

## Решение: единый слой сбора

**Кто:** объединение уникальных пар `(item_id, region)` из watchlist **всех** пользователей (дедупликация).
**Как часто:** `collect_all_active_lots` — каждые 20 сек, динамический batch
(min=5, max=50 пар за запуск), цель — полный цикл по всем парам ≤60 сек.
Сначала обрабатываются наиболее просроченные пары (`last_successful_check ASC NULLS FIRST`).
Формула батча и таблица примеров → `docs/SERVICES.md`.
**Что собирает:** полный снэпшот лотов — raw_lots, liquid/expiring split, snapshot-history matching.
**Где хранит:** `collected_data` с `user_id = NULL` (глобальная запись).
**user_id в смежных таблицах:** `market_statistics` — также `NULL` (глобальная
запись на пару item/region); `sales_history` — `NOT NULL`, но дедупликация по
`(item_id, region, sale_time)` идёт без фильтра по `user_id` (данные фактически
глобальные). Подробности полей → `docs/DATABASE.md`.
**После каждого сбора:** `_publish_signals` пересчитывает выгодные лоты и пишет в Redis
`signals:{user_id}:{item_id}:{region}:{qf}:{ef}` (TTL 300 сек). Параллельно (2026-07-20)
публикует push-события в RabbitMQ (`push.events`, DIRECT-exchange, routing_key `push`) —
низколатентный конвейер уведомлений (best-effort, не ломает сбор при недоступности брокера).
Fan-out на стороне брокера: к `push.events` привязаны ДВЕ durable-очереди с тем же
routing_key — `push.notifications` (web push, сервис `push_service`) и (с 2026-07-21)
`telegram.notifications` (сервис `telegram_bot`); брокер отдаёт копию каждого события
обоим каналам. Продюсер о получателях/каналах не знает — курация в консьюмерах.
См. `docs/SERVICES.md` (разделы «Web Push» и «Telegram»),
`docs/tasks/telegram-notifications.md`, `docs/tasks/web-push-notifications.md`.
**Эффект:** 100 пользователей следят за одним товаром → **1 API запрос**, не 100.

```
Watchlist всех пользователей:
  user1: [m02wr/RU, 04yr/RU]
  user2: [m02wr/RU, y1q9/EU]
  user3: [m02wr/RU]

Дедупликация → уникальные пары:
  m02wr/RU, 04yr/RU, y1q9/EU

Результат: 3 API запроса вместо 7
```

> **История:** ранее существовал второй слой сбора ("Лента возможностей" /
> `global_item_scan`) для discovery предметов вне watchlist — реализован и
> удалён дважды (2026-06-07, 2026-06-11). Метрика "дешевле средней цены
> выставленных лотов" оказалась методологически некорректной.
> Подробности → `docs/CHANGELOG.md`. **С 2026-08-03 второй конвейер существует
> снова** — «Лента артефактов», см. раздел ниже: метрика взята от реальных
> сделок, а область сбора сужена до ~103 артефактов.

## Второй конвейер: «Лента артефактов» (2026-08-03)

Параллельно watchlist-конвейеру работает второй сбор — **не зависящий от того, добавил ли
кто-то предмет в «Избранное»**. Он закрывает архитектурное ограничение основного конвейера
(«лоты в игре, которых нет в нашей БД»: коллектор видит только пары из `user_watchlist`), но
не в масштабе всего каталога, а по разрешимой области — артефактам.

**Кто:** все артефакты каталога (`category LIKE 'artefact%' AND on_auction IS NOT FALSE`,
~103 предмета) — набор не зависит от пользователей.
**Как часто:** `collect_artifact_lots` каждые 60 с, два темпа (горячие каждый цикл, холодные
каждый 5-й), резумируемый курсор в Redis, бюджет 200 ед/прогон, Redis-лок против наложения.
**Что собирает:** **полную** пагинацию `/lots` по `data["total"]` (в отличие от watchlist-
конвейера, который берёт первые 200 лотов) + раз в час `/history` по всем артефактам.
**Где хранит:** `feed_lots` (живой срез только выгодных лотов, переписывается каждым циклом),
`artifact_variant_stats` (статистика варианта), `sales_history` с `user_id = NULL`.

**Общие точки с основным конвейером — переиспользуются как есть, не форкаются:**

| Что | Общий компонент |
|---|---|
| HTTP + rate limit | `StalcraftClient` → `core/rate_limiter.py` (единый Token Bucket на всю систему) |
| Формулы цены/прибыли/риска | `services/analytics/pricing.py` (`compute_reference`, `make_sell_options`, `evaluate_lot_profit`, `classify_risk`, `RISK_MARGIN_MULT`) |
| Кэш ответов API | `services/cache/api_cache.py` — после обхода артефакта срез пишется в общий кэш, `GET /lots/{id}` по нему не порождает своего запроса |
| Каталог | `master_items` (`category`, `on_auction`, `lots_total`) |

Шину уведомлений (`push.events`) лента **не использует** — см. ниже.

**Расход внешнего API.** Бюджет ленты — 200 ед/мин (100 вызовов `/lots`) + ~3.4 ед/мин на
историю артефактов. Ожидаемый суммарный расход: 54.5 (текущий) + ~103.4 ≈ **158 запросов/мин
≈ 39.5 % лимита 400**. Предохранитель: перед каждым предметом задача читает фактический расход
всей системы (`stalcraft:requests:minute:*`) и прерывает цикл при превышении 340 ед/мин —
основной сбор «Избранного» имеет приоритет. Задача обязана деградировать в более длинный
цикл, а не превышать бюджет.

**Уведомлений у ленты нет (сужение объёма 2026-08-04).** Второй конвейер — конвейер
**данных**, а не доставки: он не публикует ничего в `push.events`. Тип события `feed_lot`,
его продюсер и обработчики в обоих консьюмерах удалены по решению пользователя: лента —
отдельный раздел, мониторинг ведётся напрямую с портала. Существующая трансляция
«Избранного» (`profitable_lot` / `buy_alert` / `emission`) не изменилась.

**Отказоустойчивость цикла.** Ошибка одного предмета не роняет прогон: `safe_scan_item`
ретраит транзиентную ошибку, `note_item_failure` считает подряд идущие отказы в
`feed:scan:fail:{item_id}`, а после трёх отказов предмет **паркуется** на
`FEED_ITEM_PARK_TTL = 900` с — в `feed:scan:last` пишется метка из будущего, и он уходит из
головы очереди. Иначе предмет без обновлённого `feed:scan:last` встаёт первым в каждом
следующем цикле и бесконечно жжёт лимит API своим же отказом.

**Redis-ключи ленты:**

| Ключ | Кто пишет | Смысл |
|---|---|---|
| `feed:scan:lock` | `collect_artifact_lots` | Лок цикла (NX EX 300) — beat каждые 60 с не наложится на цикл длиннее минуты |
| `feed:scan:last:{item_id}` | `collect_artifact_lots` | ISO-время последнего успешного обхода, TTL 24 ч (порядок очереди). У припаркованного предмета — метка из будущего |
| `feed:scan:fail:{item_id}` | `collect_artifact_lots` | Счётчик подряд идущих отказов предмета, TTL 1 ч; после 3 — парковка на 900 с |
| `feed:scan:cycle` | `collect_artifact_lots` | Счётчик прогонов — определяет темп холодных предметов |
| `feed:scan:sweep` | `collect_artifact_lots` | `"{цикл}:{unix_ts}"` начала текущего полного круга (метрика калибровки) |
| `feed:showcase:{region}:{порог}:{лимит}` | `GET /feed/lots` | Кэш витрины лимитированного тарифа, TTL 30 с; порог квантован вниз шагом 5 |
| `feed:summary:{region}:{порог}` | `GET /feed/summary` | Кэш сводки 24 ч, TTL 60 с |

Состояние обхода живёт в Redis, а не в БД, сознательно: оно операционное, потеря безвредна,
а UPDATE 103 строк каталога каждую минуту — лишняя запись в таблицу, которую читают все
разделы.

**Полоса сигналов ленту не показывает.** `GlobalFeed` / `MobileSignals` (общий дата-слой
`store/feedStore.ts` + `hooks/useFeedPolling.ts`) остались источником **одного** потока —
watchlist-сигналов (`GET /monitoring/signals/{item_id}`, Redis `signals:*`). Артефактные
карточки, кикер «ЛЕНТА»/«ИЗБРАННОЕ» и переход `/app/feed?lot=…&item=…` с закреплённой строкой
были реализованы и **удалены при сужении объёма 2026-08-04**; `FEED_PANEL_H` вернулся с 62 к
54, условие показа полосы (`signalsVisible`) — к прежнему: пустое «Избранное» → полосы нет.
Лента живёт целиком на своей странице `/app/feed`, куда пользователь заходит сам.

## Схема потоков данных

```
                    ┌─────────────────────────────────┐
                    │         master_items             │
                    │         (2236 предметов)         │
                    └────────────┬────────────────────-┘
                                  │
                     Уникальные пары (item_id, region)
                        из watchlist всех пользователей
                                  │
                                  ▼
                    ┌───────────────────────────┐
                    │  collect_all_active_lots   │
                    │  каждые 20 сек, дин. batch │
                    └────────────┬───────────────┘
                                  │
                                  ▼
                    ┌───────────────────────────┐
                    │       collected_data       │
                    │       user_id = NULL       │
                    └────────────┬───────────────┘
                                  │
                                  ▼
                    ┌───────────────────────────┐
                    │      Analytics Service     │
                    │  market_statistics         │
                    │  pricing.py                │
                    └────────────┬───────────────┘
                                  │
                                  ▼
                    ┌───────────────────────────┐
                    │     Redis signals:*        │
                    │     (TTL 300 сек)          │
                    └────────────┬───────────────┘
                                  │
            ┌─────────────────────┴─────────────────────┐
            ▼                                            ▼
   GET /monitoring/signals/{item_id}          Фронтенд (GlobalFeed/
                                               feedStore, LotStatCard;
                                               поллинг 30 сек)

  Параллельно уведомления: _publish_signals → RabbitMQ push.events (DIRECT)
  → fan-out → telegram.notifications (telegram_bot) + push.notifications (push_service)
  — событийная доставка; с 2026-07-21 Telegram тоже консьюмер, а не поллинг Redis.
```

Второй конвейер (с 2026-08-03) идёт рядом и не зависит от watchlist:

```
   master_items (category LIKE 'artefact%', ~103)
             │
             ▼
   collect_artifact_lots (60 с, полная пагинация /lots, бюджет 200 ед)
             │                      ▲
             │                      │ ref/риск/пачки варианта
             │        artifact_variant_stats ◄── calculate_artifact_variant_stats (:14…:54)
             │                                              ▲
             ▼                                              │ продажи 30 д
        feed_lots  (только выгодные лоты)          sales_history (user_id = NULL)
             │                                              ▲
             │                                              │
             │                                 collect_artifact_history (:15, /history)
             ▼
        GET /feed/*   (lots и variant — без гейта, ветвятся по тарифу;
                       summary и filters — гейт feed_access)

  Уведомлений у ленты нет: в push.events этот конвейер не публикует ничего.
```

## Персонализация

Сбор данных глобальный, персонализация — на уровне запроса:

| Что | Уровень |
|-----|---------|
| Цены, лоты, история | Глобальный (1 запись на пару) |
| Мин. маржа (10%) | Личный (user_settings) |
| Уведомления | Личный (user_settings) |
| Tracked batch sizes | Личный (user_watchlist) |
| Ручной refresh | Личный (user_id в collected_data) |
| Статистика по quality/enchant | На лету (фильтрация sales_history при запросе) |

### Фильтрация по quality/enchant (карточка Избранного)

`market_statistics` хранит глобальные агрегаты без разбивки по качеству/заточке.
Когда watchlist-запись имеет `quality_filter` или `enchant_filter`, три блока карточки получают данные по-разному:

| Блок | Источник | Как фильтруется |
|------|---------|-----------------|
| Выгодные лоты | `GET /lots/{id}` + фронт | `profitableLots` сравнивает `quality_name`/`enchant_level` |
| Варианты продажи | `GET /monitoring/item/{id}?quality_filter=…` | На лету: `median_price_7d`, `sales_volume_7d`, `sell_options` из отфильтрованных `sales_history`; `best_sell_hour`/`buy_hours` и проч. берутся из глобальной `market_statistics` |
| История продаж | `GET /monitoring/sales-chart/{id}?quality_filter=…` | SQL-фильтр по `additional_info->>'qlt'` / `upgrade_bonus` |

`sell_options` в режиме с фильтром считаются с `confidence=low` (только объём, без lot_start пар), поскольку выборка по одному качеству/заточке обычно мала для статистической уверенности.

## Celery-расписание и автообновление фронтенда

Актуальное расписание Celery-задач, разовые задачи и цепочка при добавлении
в watchlist → `docs/SERVICES.md`.

**Автообновление фронтенда:** `LotStatCard` и `GlobalFeed` поллят
`GET /monitoring/signals/{item_id}` каждые 30 сек — те же данные из Redis
`signals:*`, что пишет `_publish_signals`. Полный refresh страницы не требуется.
Интервалы поллинга (5 мин / 30 с / 30 с) не менялись; второго вызова в этом тике нет —
артефактные карточки полосы отменены при сужении объёма 2026-08-04. `/app/feed` поллит
`GET /feed/lots` раз в 30 с, пока страница открыта.
(Telegram-бот с 2026-07-21 читает уведомления не из Redis `signals:*`, а из
очереди `telegram.notifications` — см. `docs/SERVICES.md`.)
